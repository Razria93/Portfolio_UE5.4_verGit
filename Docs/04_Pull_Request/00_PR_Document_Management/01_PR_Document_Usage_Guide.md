# PR Document Usage Guide

현재 기준 범위: P01~P18 PR 문서

이 문서는 `02_PR_Term_Usage_Map.md`에 용어를 배치할 때 사용하는 판단 기준을 정리한다. `02_PR_Term_Usage_Map.md`가 실제 용어 목록과 문서별 사용 현황을 관리한다면, 이 문서는 각 용어를 `Only EN / Conditional EN / Only KR / EN(KR)` 중 어디에 둘지 판단하는 기준 문서다.

---

## 판단 질문

용어를 분류할 때는 먼저 다음 질문으로 판단한다.

- 이 용어를 문서에서 어떻게 표기할 것인가?
- 항상 EN으로 둘 것인가?
- 브랜치 시점 / 문서 / 문맥에 따라 조건부로 EN을 유지할 것인가?
- 항상 KR로 풀어쓸 것인가?
- 첫 등장에서는 `EN(KR)`로 병기하고 이후 EN으로 사용할 것인가?

---

## 맵 구성 기준

`02_PR_Term_Usage_Map.md`의 통합 기준과 문서별 기준은 다음 역할로 나눈다.

- `통합 용어 사용 맵`은 P01~P18 용어의 단순 합산 목록이 아니라, PR 문서 전체에 적용할 기본 용어 정책과 공통 기준을 정리한다.
- 통합 기준에는 여러 문서에서 반복되는 용어, 이후 문서에서도 재사용될 가능성이 높은 용어, 시점 제한이 필요한 위험 용어, 문서군 전체에서 표기 기준을 고정해야 하는 용어를 둔다.
- `문서별 용어 사용 맵`은 각 PR에서 실제 등장한 용어와 해당 문서 안에서의 적용 방식, 브랜치 시점 특수성, 통합 기준과 다른 override를 정리한다.
- 문서별 항목은 통합 기준의 단순 하위 목록이 아니라, 해당 PR 문서의 실제 사용 사례와 예외를 확인하기 위한 기준이다.
- 통합 기준과 문서별 기준이 충돌하면 통합 기준을 우선하되, 브랜치 시점이나 문서 목적 때문에 다른 표기가 필요하면 문서별 override로 명시한다.
- `EN(KR)`의 기능 흐름별 묶음은 PR 번호 자체가 아니라 용어가 처음 등장하는 기능 흐름 구간을 기준으로 정리한다.

---

## 1. Only EN

KR로 바꾸면 코드 / UE / 프로젝트 구조 추적성이 떨어지는 용어를 둔다. 일반 개발 / Unreal / game dev 문맥에서 보편적으로 쓰이는 기술어도 `Only EN` 후보로 본다.

### 판별 기준

- 코드나 Unreal / game dev 문서에서 이미 널리 쓰는 용어인가.
- KR로 풀면 오히려 길고 애매해지는가.
- 문서 전체에서 반복적으로 쓰이며 기술 추적성이 필요한가.
- 독자가 코드나 asset을 찾을 때 EN이 그대로 도움이 되는가.
- 첫 등장마다 KR 설명을 붙여도 독자 이해가 크게 좋아지지 않는가.

### 예시

- `BehaviorTree`
- `Blackboard`
- `Component`
- `Montage`
- `Request`
- `Result`
- `Prompt`
- `notify`
- `socket`
- `collision`
- `overlap`
- `delegate`
- `binding`
- `broadcast`

### 내부 분할 기준

- `UE / Actor / Asset`: Unreal, asset, actor 계층에서 쓰는 말.
- `Animation / Movement`: animation, locomotion, movement 설명에 쓰는 말.
- `Combat / Damage / Collision`: 전투, damage, collision, feedback에 쓰는 말.
- `Runtime Data / State`: 실행 중 값, 상태, cache, payload 같은 data / state 말.
- `Event / Delegate / Lifecycle`: event 전달, delegate, request / result, lifecycle 처리 말.
- `Execution Flow / Pipeline`: pipeline, routing, active / incoming execution처럼 실행 흐름을 설명하는 말.
- `문서 / Prompt 운영 용어`: AI Workflow, Prompt Library 같은 문서 운영 말.

---

## 2. Conditional EN

항상 EN으로 두기에는 위험하지만, 특정 시점 / 문서 / 문맥에서는 EN으로 유지해야 하는 용어를 둔다. 네 프로젝트 문서에서 반복 사용하지만 아직 고유 용어인지 애매하거나, 문맥에 따라 의미가 달라지는 넓은 용어도 이 기준으로 검토한다.

### 판별 기준

- 후속 브랜치에서 도입된 구조명이라 과거 PR에 소급하면 안 되는가.
- 문맥에 따라 KR로 풀어쓰는 게 더 나은가.
- 단독 사용하면 의미가 넓어서 대상 단어와 함께 써야 하는가.
- 같은 EN이라도 시점별 의미가 달라지는가.

### 예시

- `orchestration`: P15 이후에만 사용한다.
- `intervention`: P17 이후에만 사용한다.
- `cleanup`: `runtime cleanup`, `state cleanup`처럼 대상을 함께 쓴다.
- `Pipeline`: 제목 / 핵심 구조에서는 유지하고, 본문에서는 `흐름`을 우선한다.
- `context`: 구조체 / 판단 정보 단위에서는 EN을 유지하고, 일반 문맥 설명에서는 KR을 우선한다.
- `feedback`: `ActionFeedback`, `ReactionFeedback`처럼 구조명일 때는 EN을 유지하고, 일반 결과 표현일 때는 KR 설명을 허용한다.

---

## 3. Only KR

KR만으로 충분히 의미가 전달되고, EN으로 쓰면 문서가 기술어 나열처럼 보이는 용어를 둔다.

### 판별 기준

- 코드 식별자나 프로젝트 고유명으로 추적할 필요가 낮은가.
- 독자 경험상 KR이 더 직관적인가.
- 문서 역할 / 판단 / 결과 / 상태 설명에 가까운가.
- EN으로 쓰면 괜히 프로젝트 고유 개념처럼 보이는가.

### 예시

- `공격 단계`
- `중단 허용 조건`
- `후속 범위`
- `검증용 문서`
- `작업 운영 흐름`

### 내부 분할 기준

- `문서 구조 / 설명 역할`: 문서 안에서 설명 역할을 하는 말.
- `Gameplay 상태 / 처리 결과`: gameplay 동작 상태나 결과를 설명하는 말.
- `AI Workflow 운영 표현`: AI 작업 운영 문맥에서 KR이 더 자연스러운 말.

---

## 4. EN(KR)

기본 표기는 EN으로 유지해야 하지만, 처음 보면 의미를 모를 수 있어서 첫 등장에 KR 설명을 병기할 용어를 둔다. 네 프로젝트 안에서 특정 구조 / 책임 / 흐름을 가리키는 이름은 `EN(KR)` 후보로 본다.

`EN(KR)`은 덜 중요한 용어를 모아두는 구분이 아니다. EN을 유지해야 하지만 독자에게 최초 의미 설명이 필요한 용어를 따로 둔 것이다.

### 판별 기준

- 코드 / 문서 / 구조 추적 때문에 EN은 유지해야 하는가.
- 하지만 독자가 처음 보면 의미나 역할이 불명확한가.
- PR 안에서 반복 사용되므로 매번 KR로 풀면 문서가 장황해지는가.
- 첫 등장에만 설명하면 이후 EN만으로 읽을 수 있는가.

### 예시

- `Attachment(무기 부착 actor)`
- `Action Request(행동 실행 요청)`
- `FExecutionInterventionDirective(중단 실행 지시값)`
- `Prompt Blueprint(Prompt 기준 문서)`

### 병기 설명 단계

`EN(KR)`의 괄호 안은 항상 긴 설명일 필요는 없다. 일반 UE / game dev 기술어가 포함된 조합어는 보편 용어를 유지하고, KR은 최소 역할만 보완할 수 있다.

- 최소 역할 병기: 일반 UE / game dev 기술어가 섞인 조합어에 짧은 역할만 보완한다.
  - 예: `Attachment Overlap Event(attachment overlap 전달 event)`
- 상세 역할 병기: 프로젝트 고유 구조 / 책임 / 판단 기준을 설명해야 하는 용어에 더 구체적인 역할 설명을 붙인다.
  - 예: `FExecutionInterventionDirective(중단 실행 지시값)`

괄호 안이 EN을 그대로 반복할 뿐이면 보완 대상으로 본다.

### 내부 분할 기준

`EN(KR)` 내부의 PR 범위 표기는 PR 번호 자체가 아니라 처음 등장하는 기능 흐름 구간을 뜻한다. 권장 제목은 다음 형태다.

- `P01~P03: 플레이 기반 / 장착 준비에서 처음 등장하는 병기 대상`
- `P04~P07: Action 실행 / Damage 송신에서 처음 등장하는 병기 대상`
- `P08~P14: Damage 수신 / Reaction / Feedback에서 처음 등장하는 병기 대상`
- `P15~P17: 공용 실행 / 중단 개입 구조에서 처음 등장하는 병기 대상`
- `P18: AI Workflow / Prompt Library에서 처음 등장하는 병기 대상`

## 5. 섹션별 용어 적용 기준

PR 문서의 섹션 역할에 따라 용어 밀도를 조절한다. 같은 용어라도 섹션 목적에 따라 KR 우선, EN(KR), Only EN 적용 범위가 달라질 수 있다.

### 5.1 요약

#### 기본 방향

- PR을 처음 읽는 사람이 전문용어를 몰라도 목적과 변경 의미를 이해할 수 있게 작성한다.
- 코드 식별자, 구조체명, enum 값은 최소화한다.
- 필요한 경우 쉬운 KR 설명을 먼저 쓰고, 추적성이 필요한 용어만 괄호로 병기한다.

#### 권장 표기

- Only KR: 행동, 문제, 결과, 목적을 설명하는 말.
- EN(KR): 요약 이해에 꼭 필요한 핵심 용어.
- Only EN: Player, AI, UE, Prompt처럼 대체하면 오히려 어색한 기본 용어.

### 5.2 핵심 개념

#### 기본 방향

- 본문에서 반복 사용할 핵심 식별자를 먼저 정의한다.
- 단순 영문 목록이 아니라 `EN(KR 설명)`과 짧은 역할 설명을 함께 둔다.
- 핵심 개념에서 정의한 용어는 이후 본문에서 EN만 사용해도 된다.

#### 권장 표기

- EN(KR): PR 고유 구조명, request / result / context / rule처럼 추적성이 필요한 용어.
- Only EN: 코드 식별자, type, enum, 파일명.
- Only KR: 핵심 용어가 아니라 문장 설명으로 충분한 일반 개념.

### 5.3 변경 배경

#### 기본 방향

- 문제의 원인, 계기, 대략적인 방향성을 설명한다.
- 구현 세부 식별자보다 “왜 이 작업이 필요했는지”를 우선한다.
- 후속 브랜치에서 생긴 용어를 과거 PR 배경에 소급하지 않는다.

#### 권장 표기

- Only KR: 필요성, 책임 분리, 흐름, 상태, 문제 설명.
- EN(KR): 배경 이해에 필요한 프로젝트 핵심 용어의 첫 등장.
- Only EN: 이미 해당 문서의 핵심 개념에서 정의한 용어.

### 5.4 변경 범위

#### 기본 방향

- 각 변경 축을 `왜 / 어떻게 / 결과`로 설명한다.
- `어떻게`에서는 코드 식별자와 구조명을 사용할 수 있지만, 식별자 나열이 되지 않게 역할을 함께 쓴다.
- 같은 변경을 Feature / Refactoring / Troubleshooting에서 반복 설명하지 않는다.

#### 권장 표기

- Only EN: 코드 식별자, component / request / result / context 등 실제 구조 추적이 필요한 용어.
- EN(KR): 그 PR에서 처음 소개되는 구조명.
- Only KR: 결과, 역할, 책임, 완료 범위.

### 5.5 주요 처리 흐름

#### 기본 방향

- 분기나 순서가 중요한 흐름은 `text` 코드블럭의 `->` 흐름으로 쓴다.
- 흐름 안에서는 가능한 KR 설명을 우선하고, 핵심 개념에서 정의한 용어만 제한적으로 사용한다.
- `No / Yes` 분기는 명시한다.

#### 권장 표기

- Only EN: 핵심 개념에서 정의한 실행 주체, request, result, state.
- EN(KR): 흐름 시작 전 본문 설명에서 첫 등장하는 핵심 용어.
- Only KR: 흐름 단계 설명, 판단 결과, 후속 처리.

### 5.6 구현 결과 / 테스트 방법 / 검증 결과

#### 기본 방향

- 구현 결과는 변경 이후 보장되는 동작을 쓴다.
- 테스트 방법은 확인 절차를 쓴다.
- 검증 결과는 실제 확인된 결과를 쓴다.
- 세 섹션에서 같은 문장을 반복하지 않는다.

#### 권장 표기

- Only EN: 테스트 대상 코드 식별자, command, branch, asset name.
- EN(KR): 검증 대상 구조명이 본문에서 처음 다시 등장할 때.
- Only KR: 확인했다, 통과했다, 유지한다, 제외했다 같은 결과 표현.

### 5.7 관련 문서 / 정리

#### 기본 방향

- 관련 문서 섹션명은 `## 관련 문서`로 통일한다.
- 정리는 앞 섹션 요약 반복이 아니라 해당 PR의 최종 의미만 남긴다.

#### 권장 표기

- Only EN: 파일명, 문서 ID, 브랜치명.
- EN(KR): 문서 체계 용어가 처음 등장할 때.
- Only KR: 관련 이유, 후속 범위, 완료 의미.

---

## 적용 기준

- 새 용어가 등장하면 먼저 이 문서의 판별 기준으로 분류한다.
- 분류가 끝난 용어는 `02_PR_Term_Usage_Map.md`의 통합 용어 사용 맵이나 문서별 용어 사용 맵에 반영한다.
- 브랜치 시점이 중요한 용어는 `Conditional EN` 또는 문서별 override로 관리한다.
- 판단이 애매한 용어는 즉시 확정하지 않고 audit 후보로 남긴다.
- H2 / H3 제목에 들어가는 EN은 병기하지 않고, 본문 첫 등장에서 필요한 경우에만 EN(KR)로 병기한다.
- 코드 식별자, 함수명, enum 값, 파일명, 브랜치명은 inline code로 감싼다.
- 일반 UE / game dev / 문서 도메인 용어는 inline code로 감싸지 않는다.
- 문서 PR처럼 변경 성격이 하나로 충분히 설명되는 경우에는 `Documentation` 단일 카테고리를 허용한다.
