# Project Rules Draft

## 1. 목적

본 문서는 프로젝트에서 사용할 프롬프트와 협업 규칙을 체계적으로 구성하기 위해, 작업 단계와 각 단계에서 필요한 요청 방식을 정리하는 초안이다.

기능 개발, 리팩터링, 검증, 문서화 과정에서 AI가 어떤 기준으로 사용자의 의도를 해석하고 작업을 분리해야 하는지 구상하는 것을 목표로 한다.

---

## 2. 작업 단계 구상

프로젝트 작업은 크게 다음 4단계로 구분한다.

```yaml
1. 기획
2. 기술 구현
3. QA
4. 문서화
```

이 4가지는 역할자가 아니라 작업 단계다. 실제 책임 주체는 사용자와 Codex이며, Prompt / History / Document / Work Checklist는 작업을 통제하고 기록하기 위한 운영 산출물로 본다.

---

## 3. 단계별 기능

### A. 기획

기획 단계는 사용자의 아이디어를 구현 가능한 기술 목표로 바꾸는 단계다.

```yaml
기획 요청
-> 아이디어 / 참고 기능 / 목표 전달
-> 자연어 요청을 기술적 언어로 해석
-> 구현 단계 분리
-> 구현 우선순위 결정
-> 비범위와 후속 작업 후보 분리
-> 기술 구현 요청으로 연결
```

기획 단계에서는 바로 구현에 들어가지 않고, 사용자가 자연어로 전달한 의도를 AI가 시스템, 객체, 실행 흐름, 검증 기준으로 나누어 정리한다.

### B. 기술 구현

기술 구현 단계는 분리된 구현 요청을 실제 코드와 구조로 연결하는 단계다.

```yaml
기술 구현 요청
-> 관련 객체 / Component / Subsystem / Asset 연결 지점 탐색
-> 구조 및 흐름 아이디어 제안
-> 사용자와 접근 방식 결정
-> 최소 API와 데이터 구조 구성
-> 호출 연결과 기본 흐름 확인
-> 정책 아이디어 제안
-> API와 구조체 구체화
-> 기능 단위 구현
-> QA 요청 및 안정성 확인
-> 구조 / 파일 정리와 후속 보강 항목 분리
```

기술 구현은 한 번에 완성 기능을 만드는 것이 아니라, 먼저 연결 가능한 최소 구조를 만들고 이후 정책과 세부 동작을 구체화하는 흐름을 우선한다.

### C. QA

QA 단계는 구현 결과가 기대한 흐름을 만족하는지 확인하는 단계다.

```yaml
QA 요청
-> Build 확인
-> Code Flow 확인
-> PIE 확인
-> Editor / Asset 확인
-> 실패 원인 기록
-> 미검증 항목 기록
-> 다음 조치 제안
```

QA는 단순히 "문제가 없는지" 확인하는 단계가 아니라, 어떤 항목을 실제로 검증했고 어떤 항목은 확인하지 못했는지 분리하는 단계다.

### D. 문서화

문서화 단계는 작업 결과와 판단 근거를 목적에 맞는 산출물로 정리하는 단계다.

```yaml
문서화 요청
-> Work Checklist
-> Bug Report
-> System Architecture
-> Technical Document
-> PR Document
-> Verification Log
```

문서화 요청은 별도 역할이 아니라, 기획 / 기술 구현 / QA 이후 필요한 산출물을 작성하는 요청으로 본다.

## 4. 예시: 스텔라 블레이드 Blink / Impulse 요청의 기술적 해석

이 예시는 AI가 자연어 요청을 기술적 작업 단위로 해석하고, 부족한 조건을 확인 질문으로 분리하는 방식을 보여주기 위한 것이다.

### 사용자 요청 예시

```text
적에게서 파란색 빛이 보이면
몇 초 뒤에 플레이어의 무기에서도 파란 빛이 나오고,
그 뒤 일정 시간 동안 정해진 커맨드를 입력하면
월드 혹은 대상이 느려지면서
캐릭터가 화면에서 입자가 되어 사라진다.

카메라는 적 후방으로 돌아가고,
입자가 모이면서 캐릭터가 다시 화면에 서서히 나타난다.
```

### 기술적 해석 예시

```yaml
Enemy Signal
-> Enemy가 특정 Montage 재생
-> AnimNotify에서 특정 Socket 기준 Signal VFX 실행
-> 일정 시간 뒤 Player에게 Reaction Signal 전달

Player Reaction Window
-> Player가 Reaction Signal 수신
-> 제한 시간 동안 Reaction Window 활성화
-> Command Queue에 입력 수집
-> 정해진 입력 순서와 비교

Success Execution
-> 성공 시 Slow Motion 또는 대상별 PlayRate 조정
-> Player Disappear VFX 재생
-> Player Mesh Visibility 비활성화
-> Enemy 후방 위치 계산
-> Camera Transition 실행
-> Player 위치 재배치
-> Reappear VFX 재생
-> Player Mesh Visibility 활성화
-> State Restore 실행
```

### 확인 질문 예시

```yaml
확인 질문
-> 감속 중 피격 판정은 어떻게 처리할 것인가?
-> Player가 사라진 동안 Collision은 유지할 것인가?
-> 입력 실패 / 만료 / 중단 시 어떤 상태를 복구해야 하는가?
-> Enemy 후방 위치는 어떤 기준으로 계산할 것인가?
-> World Time Dilation과 개별 PlayRate 중 어떤 방식을 사용할 것인가?
-> Camera 이동 중 입력은 잠글 것인가?
```

## 5. Prompt 구성 구상

AI 협업 규칙은 다음 층위로 나눌 수 있다.

```yaml
Prompt 구성 후보
-> Unreal 전역 Prompt: Unreal Engine C++ 설계와 구현 관례
-> 프로젝트 Prompt: Project Stella 단위의 작업 규칙과 구조 기준
-> 단계별 공용 Prompt: 기획 / 기술 구현 / QA / 문서화 단계별 요청 기준
-> 기능별 Prompt: 특정 기능 작업을 재개하거나 구체화하기 위한 요청 기준
```

Prompt는 AI에게 단순히 작업을 맡기는 문장이 아니라, 사용자의 의도를 일관된 작업 방식으로 해석하게 만드는 규칙으로 둔다.
