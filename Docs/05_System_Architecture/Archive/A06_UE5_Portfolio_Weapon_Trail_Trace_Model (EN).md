# Weapon Trail Trace Model

## 1. Purpose

This document summarizes the meaning and cost of the `weapon trail trace` approach for calculating melee weapon hit positions.

The current melee hit detection structure detects targets through weapon collision overlap.

However, in an overlap-based structure, the `SweepResult` from `OnComponentBeginOverlap()` does not always provide a meaningful hit position.

In particular, when a weapon actor is attached to a character mesh socket and moves by animation transform, `bFromSweep == false` can naturally occur.

Therefore, if hit VFX / hit SFX / hit direction / guard / parry surface handling need more accurate hit positions, the hit position calculation method should be reviewed separately.

---

## 2. Current Overlap-Based Method

The current structure lets the weapon actor collision component generate an overlap event, and `ACWeaponActor` converts it into `FHitContext`.

The basic flow is as follows.

```text
Weapon collision overlap
-> ACWeaponActor::OnComponentBeginOverlap()
-> FOverlapContext
-> FHitContext
-> UCApplyDamageComponent::RequestApplyDamage()
-> ApplyDamage / TakeDamage / Reaction / Feedback
```

The main role of this method is target detection.

In other words, it is suitable for determining whether the weapon collision and target collision are overlapping.

However, it has limitations when calculating a hit point.

The `SweepResult` from `OnComponentBeginOverlap()` can contain meaningful values when the overlap was generated by sweep movement.

In the current weapon collision structure, the collision is usually not moved directly with `MoveComponent(..., bSweep=true)`, but updated through socket / attachment / animation transform.

Therefore, even when an overlap occurs, `bFromSweep == false` can occur, and in that case `SweepResult.ImpactPoint` is difficult to trust.

---

## 3. Why bFromSweep Can Be False

`bFromSweep == false` means the overlap was not produced by sweep movement.

In the current melee weapon structure, the following cases are common.

- The weapon actor is attached to a character mesh socket and moves according to the animation pose.
- The collision is enabled at hit window begin and overlaps a target that was already intersecting.
- A physics overlap pair is newly detected after transform update.
- The collision component was not moved by a sweep movement API.

In these cases, the overlap itself is valid, but the engine was not in a situation where it produced a sweep hit result.

Therefore, `SweepResult.ImpactPoint` can be empty or inaccurate.

This should be considered a characteristic of the current overlap-based melee hit detection method rather than a bug.

---

## 4. Closest Point Fallback

The first fallback is to use `GetClosestPointOnCollision()` to calculate an approximate hit point on the target collision surface.

Example:

```cpp
const FVector queryLocation = InOverlapContext.OverlappedComponent->GetComponentLocation();

FVector closestPoint = FVector::ZeroVector;
const float distance = InOverlapContext.OtherComponent->GetClosestPointOnCollision(
	queryLocation,
	closestPoint
);
```

This method calculates the closest point from the weapon collision position to the target collision surface.

It has the following meaning.

```text
Weapon collision center
-> Target collision surface closest point
```

This is not an exact blade contact point, but it provides a more natural hit position fallback than spawning VFX at the actor location.

If the target component is a capsule, the result is also calculated based on the capsule surface.

Therefore, this method does not accurately match the actual skeletal mesh body surface or a specific bone position.

---

## 5. Weapon Trail Trace Method

`weapon trail trace` is not a single built-in engine feature name. It is a melee hit detection pattern made by combining trace / sweep APIs.

The core idea is to define several sample points on the weapon and trace between each sample point's previous position and current position.

Example:

```text
Blade_Base previous position -> Blade_Base current position
Blade_Mid previous position  -> Blade_Mid current position
Blade_Tip previous position  -> Blade_Tip current position
```

For each segment, a trace such as `SphereTraceMulti()` is performed.

Although it is called `SphereTrace`, its practical meaning is as follows.

```text
Radius R sphere swept from Start to End
-> capsule-like swept volume
-> find objects overlapping or blocking that swept volume
```

In other words, it creates a capsule-like query volume with a radius between two points, then finds objects that collide with that volume.

---

## 6. Difference Between Overlap and Trail Trace

The overlap method checks whether a collision volume surrounding the weapon shape overlaps the target collision.

The trail trace method checks the movement paths of several sample points on the weapon over time.

The difference is as follows.

```text
Overlap
-> weapon collision volume itself detects overlap
-> suitable for target detection
-> may not provide an accurate ImpactPoint

Trail Trace
-> several sample points trace their previous-current paths
-> easier to obtain hit point / hit normal / bone / surface data
-> approximates the weapon shape through swept volumes of sample points
```

Therefore, trail trace is closer to changing hit detection metadata than simply improving hit position.

---

## 7. Empty Space Problem in Trail Trace

Trail trace does not mathematically check the full volume of the weapon itself.

It approximates the weapon path by combining the trace volumes of sample points placed on the weapon.

Therefore, if the sample spacing is wide and the trace radius is small, empty space can exist between samples.

In theory, a small target can pass between samples and avoid detection.

Possible mitigations are as follows.

- Increase the number of sample sockets.
- Increase the trace radius.
- Consider box trace / capsule trace instead of sphere trace.
- Consider a shorter tick interval or sub-step for fast attacks.
- Place multiple sample points along the blade length, not only blade root / mid / tip.

However, if the trace radius is too large, hits can occur wider than the actual weapon shape.

If the number of samples is too high, trace cost and duplicate hit filtering cost increase.

Therefore, trail trace requires tuning between precision and cost.

---

## 8. Cost and Implementation Burden

Trail trace has higher cost and implementation burden than the existing overlap-based structure.

Required additional elements are as follows.

- Trace sockets / sample points must be configured on the weapon mesh or weapon actor.
- Previous locations of sample points must be stored during the hit window.
- The path between current location and previous location must be traced in tick or notify tick.
- Trace results must be converted into `FDamageImpactInfo`.
- Duplicate hit target handling must be integrated with the existing hit window policy.
- Debug draw / trace channel / ignored actor policies must be organized.
- Compensation is needed to reduce misses during fast attacks or low frame rate situations.

In other words, trail trace is not simply a change to VFX position. It changes the basis of melee hit detection.

If trail trace is added while keeping the current overlap-based collision, two hit detection methods will coexist.

Therefore, when introducing it, it should be decided whether overlap will continue to be used for target detection, or whether trail trace will replace target detection as well.

---

## 9. Recommended Direction for This Project

At the current stage, it is more appropriate to introduce `FDamageImpactInfo` and the closest point fallback first, rather than immediately introducing trail trace.

The first recommended flow is as follows.

```text
Weapon overlap
-> FHitContext
-> FDamageImpactInfo
   - use SweepResult if bFromSweep == true
   - use GetClosestPointOnCollision fallback if bFromSweep == false
-> ApplyDamagePayload / Context
-> FDefaultDamageEvent
-> TakeDamagePayload / Context
-> DamageFeedback
```

This method keeps the current overlap-based hit detection metadata while improving hit VFX position.

The current `ReactionFeedback` structure matches feedback by reaction type / damage spec key / timing / trigger key.

Therefore, in the current implementation, `FDamageImpactInfo` should be directly consumed by `DamageFeedback`.

Trail trace should be introduced when the following requirements become clear.

- Accurate impact point based on weapon path is required.
- Hit normal / surface / bone data must be obtained reliably.
- Guard / parry / weapon clash strongly depends on hit position and direction.
- The overlap-based hit point fallback is inaccurate during fast weapon swings.
- Socket path-based detection provides more consistent gameplay results than weapon collision volume.

Therefore, the current conclusion is as follows.

```text
First implementation
-> Keep overlap + FDamageImpactInfo + ClosestPoint fallback

Future extension
-> Review Weapon Trail Trace as a separate hit detection model
```

---

## 10. Responsibility Placement

The responsibility for calculating hit position is most naturally placed in `ACWeaponActor`.

`ACWeaponActor` knows both the original overlap event and the weapon collision information.

Therefore, it can access the following information.

- weapon collision component
- target component
- sweep result
- hit window id
- weapon / action context
- socket or sample point transform
- weapon sample location from the previous frame

On the other hand, `UCApplyDamageComponent` is the layer that processes the damage pipeline.

Therefore, rather than calculating hit points again, it is more appropriate for it to receive `FHitContext` or `FDamageImpactInfo` and copy it into payload / context.

The recommended responsibility split is as follows.

```text
ACWeaponActor
-> create hit event
-> calculate hit point / hit normal
-> build FDamageImpactInfo

UCApplyDamageComponent
-> pass DamageImpactInfo into ApplyDamagePayload / Context
-> copy it into FDefaultDamageEvent

UCTakeDamageComponent
-> preserve DamageImpactInfo in TakeDamagePayload / Context

DamageFeedback
-> use TakeDamagePacket.Context.DamageImpactInfo
```

With this structure, ApplyDamage and TakeDamage keep the damage calculation domain, while hit event metadata is transferred as a separate structure.
