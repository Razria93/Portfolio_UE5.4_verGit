# AIStateComp 방식 vs BB-BT 방식 비교

## 목적

- `Component 방식`과 `BB-BT(Blackboard–BehaviorTree) 방식`을 **상태**와 **행동 설계**의 관점에서 비교함
    
- 결과적으로 본 프로젝트에서는 **BB-BT를 행동 설계의 중심으로 두고**, **컴포넌트는 보조 시스템으로 활용하는 하이브리드 구조**를 채택하고자 함


---

## 용어 정리

### 1. Component 방식
  
- `Blackboard`가 **데이터을 저장**하고 `AIStateComponent` 등 `Component`가 **데이터를 변경**하며 `BehaviorTree`가 **변경된 데이터를 사용하여 행동을 결정**하는 형태
    
- 상태 전환, 이벤트 처리(피격, 패턴 전환 등)가 **Component 내부 로직에 집중**됨
    
- `Player`의 `CStateComponent`와 **구조적 대칭성**을 갖도록 설계 가능

#### 핵심 정의

- 데이터 저장 / 변경 / 사용의 책임이 분리된 형태

- `Player`의 구조와 대칭성을 가짐


---

### 2. BB-BT 방식 (Blackboard–BehaviorTree)

- `Blackboard`가 **데이터를 저장**하고 `BehaviorTree`가 **데이터를 변경과 사용**을 동시에 하는 형태

- `BehaviorTree`가 조건(`Decorator`), 분기(`Selector`), 실행(`Task`)을 통해 상태를 변경하고 행동을 결정하는 구조
    
- 상태 값의 변경 역시 **BT 노드(Task/Service)를 통해 이루어짐**
    
- 행동 설계가 **에셋(BT) 단위로 시각화 및 관리**됨


#### 핵심 정의  

- `BehaviorTree`에서 데이터 변경 및 사용을 모두 책임지는 형태

- AI 행동 설계가 `BehaviorTree` 에셋 내 에서 모두 이루어짐


---

## 핵심 비교 요약

| **구분**            | AIStateComponent 방식 | BB-BT 방식            |
| ----------------- | ------------------- | ------------------- |
| **상태(State) 소유**  | Component           | Blackboard          |
| **행동 결정 주체**      | Component Logics    | BehaviorTree        |
| **상태 변경 위치**      | C++ 코드              | BT 노드(Task/Service) |
| **Blackboard 역할** | 보조 저장소              | 단일 데이터 소스           |
| **확장 방식**         | Component 수정        | 노드/데코레이터 조합         |
| **시각화/디버깅**       | 코드 중심               | BT 그래프 기반           |
| **엔진 철학 부합도**     | 커스텀 구조              | UE AI 인프라 중심        |


---

## AIStateComponent 방식 평가

### 장점

- 책임이 명확하게 분리되어 있어 **일관된 처리 흐름을 유지**할 수 있음
    
- `Player`–`Enemy` 간 **State 관리 구조를 대칭적으로 유지**할 수 있음
    
### 단점

- AI 유형·패턴이 증가할수록 **컴포넌트 책임이 비대해질 위험**
    
- `BehaviorTree`와 분리될 경우 **UE 제공 AI 인프라 활용도가 감소**
    
- 행동 흐름 설계 및 수정 시 반드시 컴포넌트의 코드가 수정되어야 하기 때문에 **확장성이 떨어짐**


---

## BB-BT 방식 평가

### 장점

- 언리얼 엔진의 **AI 설계 철학과 직접적으로 일치**
    
- 행동 로직을 **노드 / 데코레이터 / 서비스 단위로 분리하여 구성**하기 때문에 확장 및 수정이 용이함
    
- `Blackboard`와 `BehaviorTree` 에셋 내부에서 상태 정의 및 활용이 모두 이루어지기 때문에 **의사결정 흐름이 명확함**
    
- 그래프 기반 구조로 **시각화 및 디버깅에 강점**
    
### 단점

- 노드/서비스가 과도해질 경우 **트리 복잡도 증가**
    
- 데이터 수집·연산 로직까지 BT 내부로 들어오면 **Task/Service의 책임이 비대해질 수 있음**


---

## 구조 결정

- **행동 결정 / 우선순위 / 분기**  
    → `BehaviorTree`
    
- **상태 데이터 저장**  
    → `Blackboard`
    
- **데이터 수집 / 계산 / 외부 시스템 요청**  
    → `Compnent`

#### 핵심 정의

- `BlackBoard`는 상태 및 데이터를 저장

- `Component`는 판단에 필요한 데이터를 수집 및 연산

- `BehaviorTree`는 수집 된 데이터를 기반으로 상태값을 변경하고 적절한 행동을 실행


---

## 결론

- AIStateComponent 방식은 **구조적으로 타당하고 명확한 상태 제어**라는 장점을 가지지만 확장성과 수정 편의성이 낮을 수 있음

- UE의 AI 인프라 활용도, 확장성, 디버깅 측면에서는 **BB-BT 중심 구조가 더 합리적임**

- 따라서 본 프로젝트에서는 **BB-BT를 행동 설계의 중심으로 두고**, **컴포넌트는 보조 시스템으로 활용하는 하이브리드 구조**를 채택하고자 함
