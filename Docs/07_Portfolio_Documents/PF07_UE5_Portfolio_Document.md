## 1. 문서 목적

본 문서는 프로젝트 구현 과정에서 AI를 활용해 작업 내용을 정리하고, 변경 범위를 추적하며, 문서와 Git 기록을 일관되게 유지한 방식을 설명한다.
구체적으로는 AI를 구현 중 발생한 논점, 로그, 변경사항, 문서 초안을 빠르게 구조화하고 다음 작업 단위로 정리하는 데 사용했다.

---
## 2. 활용 범위

AI는 다음 작업에 활용했다.

1. 작업 흐름 정리
2. 변경 범위 검토
3. 변경 범위 정리
4. 버그 분석 정리
5. 문서화 및 Git 정리

이 문서에서는 위 활용 범위를 중심으로 AI가 개발 흐름에 어떤 방식으로 연결되었는지 설명한다.

---
## 3. 작업 흐름 정리

**관련 문서 항목**

- `05_System_Architecture`
- `07_Portfolio_Documents`

**관련 문서 예시**

**Player와 AI의 Reaction 구조 단일화 관련**

- `M05-S02`: Reaction Pending Removal and AI Observation Architecture Decision
	링크: https://github.com/Razria93/Portfolio_UE5.4_verGit/issues/49#issue-4412602387

**활용 내용**

구현 과정에서 구조 변경이 길어질 경우, 현재 작업 상태와 남은 논점을 시스템 설계 문서로 정리했다.

```text
[시스템 설계 문서 구성요소]
- 현재 구조
- 발생한 문제
- 설계 논점
- 변경 방향
- 남은 과제
```

정리된 설계 문서는 이후 포트폴리오 기술 문서로 다시 압축했다.

```text
[기술 문서 재구성 기준]
- 문서 목적
- 문제 정의
- 책임 구조
- 처리 흐름
- 문제 해결
- 정리
```

이 방식을 통해 작업이 장기화되어도 현재 변경이 어떤 문제를 해결하기 위한 것인지 유지할 수 있었고, 리팩터링 당시의 설계 의도도 이후 문서에서 다시 추적할 수 있었다.

## 4. 변경 범위 검토 및 변경 범위 정리

**관련 문서 항목**

- `01_Work_List`
- `99_Legacy/Issue_CheckList`
- `04_Pull_Request`

**관련 문서 예시**

**Reaction orchestration 구조 구축 관련**

- `D17_UE5_Portfolio_Issue_Checklist`
	링크: https://github.com/Razria93/Portfolio_UE5.4_verGit/issues/46#issue-4355773449
	
- `P16_UE5_Portfolio_Pull_Request`
	링크: https://github.com/Razria93/Portfolio_UE5.4_verGit/pull/47#issue-4408323958

**활용 내용**

코드 수정 전에는 issue checklist를 기준으로 해결하려는 문제, 현재 구조, 예상 수정 범위, 위험 요소를 먼저 정리했다.

```text
[체크리스트 문서 구성요소]
- 목표
- 브랜치명
- TODO 리스트
- 검증 기준
```

수정 이후에는 pull request 문서를 기준으로 실제 변경된 파일, 변경된 책임, 테스트 결과, 후속 작업을 다시 정리했다.

```text
[PR문서 구성요소]
- 요약
- 완료 작업
- 검증 결과
- 후속 작업
```

이 방식은 Action / Reaction execution 구조처럼 여러 component, executor, notify, data structure가 함께 영향을 받는 작업에서 특히 유용했다.

예상 변경 범위와 실제 변경 범위를 분리해 기록하면서, 처음에 예측하지 못했던 영향 범위와 추가로 정리해야 할 책임 경계를 확인할 수 있었다.

## 5. 버그 분석 흐름 정리

**관련 문서 항목**

- `02_Bug_Report`
- `07_Portfolio_Documents/PF06_UE5_Portfolio_Document`

**관련 문서 예시**

**Action / Reaction intervention window 관련**

- `M05-B04`: Action / Reaction intervention window 설정 누락 및 notify state 구간 문제
	링크: https://github.com/Razria93/Portfolio_UE5.4_verGit/issues/54#issue-4429079657

**활용 내용**

버그 재현 과정에서 나온 현상, 로그, 기대 결과, 실제 결과를 버그 리포트 형식으로 정리했다.

```text
[버그 리포트 문서 구성요소]
- 현상
- 재현 조건
- 기대 결과
- 실제 결과
- 핵심 원인
- 해결 방향
- 검증 결과
```

특히 AI를 통해 기록이 필요할 때마다 해당 문서를 갱신하는 방법을 사용함으로서 버그 발견 초기부터 문서를 갱신하여 완성한다.

이로 인해 현상 인식부터 원인 파악, 시행착오 과정, 해결 완료의 내용이 문서에 자세히 기록되기에 버그 리포트의 디테일이 높아진다.

## 6. 문서화와 Git 정리

AI는 구현 내용을 문서와 Git 기록으로 정리하는 과정에도 사용했다.

특히 긴 리팩터링 작업에서는 코드 변경, 문서 변경, asset 변경을 구분하여 커밋 단위를 잡는 데 도움이 되었다.

---
## 7. 활용 효과

AI를 사용하면서 얻은 효과는 다음과 같다.

1. system architecture를 통해 장기 리팩터링 과정의 작업 맥락과 설계 의도를 유지할 수 있었다.
2. issue checklist를 통해 코드 수정 전 예상 변경 범위와 검증 기준을 먼저 정리할 수 있었다.
3. pull request 문서를 통해 실제 변경 범위, 검증 결과, 후속 작업을 다시 정리할 수 있었다.
4. bug report를 구현 중 계속 갱신하면서 현상, 원인, 시행착오, 해결 과정을 누락 없이 기록할 수 있었다.
5. 기술 문서를 통해 구현 중 작성한 설계 기록과 버그 리포트를 제출용 설명 자료로 다시 압축할 수 있었다.
6. 문서와 Git 기록을 함께 정리하면서 코드 변경, 문서 변경, asset 변경의 작업 단위를 구분하기 쉬워졌다.

---
## 8. 정리

이 프로젝트에서 AI는 구현 과정에서 발생한 논점, 변경 범위, 버그 분석, 문서 초안을 산출물 형태로 정리하는 데 사용했다.

작업 전에는 issue checklist로 예상 작업 범위를 정리하고, 작업 후에는 pull request 문서로 실제 변경 범위와 검증 결과를 정리했다.

버그가 발생했을 때는 bug report를 통해 현상과 원인 분석 과정을 계속 갱신했고, 이후 기술 문서에서는 이 기록을 포트폴리오 설명에 맞게 다시 압축했다.

이를 통해 코드 구현, 문제 분석, 문서화, Git 기록이 서로 분리되지 않고 같은 작업 흐름 안에서 관리될 수 있었다.
