## 공개 영상 구성

게시 영상은 다음 네 묶음을 권장한다. 길이는 편집 권장값이며 촬영 원본의 제한이 아니다. 각 기술 사례는 독립된 챕터와 타임스탬프를 갖는다.

| 영상 | 권장 길이 | 내용 | 과거 19페이지 초안 대응 |
| --- | --- | --- | --- |
| 전투 플레이 | 90~150초 | 보스전·콤보·방어·회피·반격·처형·다수 적 전투, 일반 HUD 유지 | 1~3 |
| 전투 처리 구조 | 3~5분 | 일반 타격·패링·공격 중단, 저스트 회피와 카운터, 균형 붕괴와 처형 | 10~15 및 기능 설명 문서 |
| AI와 디버그 도구 | 2~4분 | 역할 배정·개별 행동·수색·복귀, 관찰 대상과 표시 설정 조작 | 16~19 |
| 트러블슈팅 검증 | 2~3분 | 가드 종료 피격·후방 피격 대응·인지 지연의 전후 비교 | 4~9 |

어택 페이싱·넉백·소켓 전환·HUD는 관련 챕터 끝에 짧게 붙이거나 보조 영상으로 분리한다. 모든 촬영 단위를 별도 게시 영상으로 만들지 않는다. 기존 영상으로 입증되는 사례를 새로 촬영할 필요는 없다.

## 촬영 전 준비

1. HUD 샘플 자원 연동과 보스전 구성을 완료한 뒤 대표 플레이 최종본을 촬영한다. 기존 전투 구조·AI·디버그 근거 촬영은 먼저 진행해도 된다.
2. 버전·작업 트리 변경·빌드·맵·Player/Enemy BP·Montage·DataAsset·주요 설정을 기록한다. HEAD만 같아도 실행 파일과 에셋이 다르면 같은 조건이 아니다.
3. 디버그 영상은 non-Shipping 환경과 `ACDebugOverlayHUD` 연결을 사용한다. Editor 패널 설정은 세션별로 다시 확인한다.
4. 녹화는 1920×1080 이상을 권장한다. 60fps가 안정적으로 유지되는 환경이면 사용하고, 그렇지 않으면 해상도·프레임 설정을 조정한 뒤 기록한다. 이 권장 녹화 조건을 성능 재측정 조건으로 대체하지 않는다.
5. 상태 글자가 읽히는 짧은 시험 녹화를 확인한다. 한 사건 전후 2~3초 여유를 확보하고, 비교 장면은 같은 카메라와 실제 동일 조건을 우선한다.
6. 내부 검증 영상은 상태 패널과 로그를 필요한 것만 켠다. 여러 Enemy를 동시에 표시하는 경우는 역할 분포를 입증하는 장면으로 제한한다.

## 오버레이를 근거로 사용하는 방법

| 자료 | 입증할 수 있는 내용 | 주의할 해석 |
| --- | --- | --- |
| 일반 게임 화면·HUD | 실제 동작, 효과, HP·균형 변화 | 단일 정지 화면으로 전후 변화나 내부 호출 순서를 확정하지 않음 |
| Character Details | 관찰 Actor의 현재 상태, 최근 판단, 기능별 진단 | 현재 값과 마지막 이벤트 값의 시점이 다를 수 있음 |
| Event Log | 수집된 사건의 이력과 판단 결과 | `Accept` 또는 `Start` 결정만으로 Executor가 실제 시작했다고 단정하지 않음 |
| World Summary | 대상별 역할 배정 수·상한과 요약 | 교전 배정 수는 동시 공격자 수가 아님 |
| 월드 드로우 | 역할·위치·방향·범위, 기능별 계획과 실제 이동 | 모든 선이 실제 이동 궤적은 아님. 색상·기준점 의미를 기능별로 설명 |
| 원본 실행 로그 | Executor 시작·종료, 결과 일련번호, 상세 처리 | 영상과 Actor·시각·사건 식별자가 연결되어야 함 |
| CSV·측정 로그 | 정해진 조건의 성능 수치 | 디버그를 켜고 녹화한 영상으로 기존 성능 수치를 다시 측정한 것처럼 설명하지 않음 |

`HUDVisible`, `CaptureEnabled`, 패널 표시, 기능별 진단·Draw 옵션은 서로 다르다. `CaptureEnabled 0`은 이후 이벤트 수집을 멈추며 게임 상태를 고정하지 않는다. CounterRush 드로우는 Action 쪽에서 호출되므로 `HUDVisible 0`만으로 숨겨지지 않는다. 정확한 조합은 [설정 문서](stellar_capture_presets.md)를 따른다.

표의 설정 이름은 설정 문서의 프리셋에 대응한다. 사건을 확인하는 동안 해당 Actor를 Focus로 고정한다. 패링·처형처럼 양측 기록이 필요한 사례는 적 1명 환경에서 Event Scope를 World로 사용한다.

### 일반 타격과 패링

일반 타격은 충돌 전후의 양측 상태를 읽을 수 있는 단발 공격을 우선한다. 반복 콤보는 대표 플레이에서 보여주고, 내부 구조 설명에는 한 사건을 사용한다.

패링은 남은 균형이 바로 0이 되지 않는 단발 사례를 먼저 촬영한다. HP 전후 동일, 패링 판정, Player 반응, 공격자 Enemy의 균형 변화를 같은 사건으로 연결한다. 균형 붕괴는 별도 후속 장면으로 분리한다. 패링 구간이 열린 사실과 패링 성공을 구분한다.

### 공격 중단

현재 공격과 중단 허용 구간이 먼저 보이도록 녹화한다. 가능하면 무기 충돌이 열린 상태에서 중단되는 사례를 선택한다. 중단 요구와 허용 판단, 기존 Action의 종료, Hit Reaction 시작을 연결한다.

추가 비교는 동일 공격에서 중단이 허용되지 않는 시점의 피격이다. 실제 정책 결과를 확인하고, 다른 이유의 거절을 중단 금지의 근거로 사용하지 않는다. Montage·충돌·잔상·실행 정보의 전체 정리는 코드 근거도 연결한다. 화면의 이펙트 소멸만으로 모든 런타임 객체 정리를 증명하지 않는다.

### 저스트 회피와 카운터 러시

일반 회피 성공과 저스트 회피 성공을 먼저 구분한다. 저스트 회피 후 실제 카운터 입력 가능 구간에서 실행하고, 가능 구간 밖에서는 실행되지 않는 비교를 짧게 추가한다. 임의로 문서의 과거 시간값을 현재 Montage 설정값으로 사용하지 않는다.

CounterRush 드로우에서 계획 방향·끝점과 실제 이동 경로를 구분한다. 현재 구현은 시작 시 확정한 위치·방향으로 이동하므로 지속 유도로 설명하지 않는다. 벽 앞 이동 제한은 보조 검증으로 적합하다. 현재 거리·방향·기회 조건을 바꿔 성공 화면을 만드는 대신 실제 설정을 기록한다.

### 균형 붕괴와 처형

일반 처형은 피해 확정 후 대상이 회복·전투 복귀하는 구간까지, 즉사 처형은 사망 결과까지 확보한다. 두 경로에 필요한 실제 데이터와 Montage가 준비되어 있는지 먼저 확인한다.

화면에는 HP·남은 균형·처형 가능 아이콘을, 내부 화면에는 Source/Target 세션 상태·종류·일련번호를 남긴다. 저체력 강조는 즉사 체력 조건이며 거리·방향을 포함한 전체 처형 가능 여부는 아니다. 처형하지 않고 기회가 만료된 뒤 복귀하는 장면은 보조 자료로 확보할 수 있다.

### 전투 참여와 AI

먼저 넓은 화면에서 링·역할 텍스트·World Summary를 보여준다. 다음에는 Enemy 한 명에 Focus를 고정하고, Perception/HitReactive 근거·배정 역할·실제 AI 행동을 확인한다. 피격 근거 없는 후보를 때렸다는 이유만으로 추가 교전 배정을 단정하지 않고, 실제 Admission과 상한을 확인한다.

보존 초안에서 PPT 16~17페이지의 Base 2 + Extra 1은 과거 사진의 설정으로 기재되어 있다. 최신 PPT·사진의 대응은 재확인 대상이다. 현재 main 초기값은 **Base 2 / Extra 최대 3 / 전체 5 / Alert 6 / Observe 12**이며 도움말과 일치한다. 1 / 2 / 3 / 1 / 1은 미채택 AI 튜닝값이다. 촬영 시 런타임 조회값을 기록하고 과거 사진 설정과 구분한다.

HitReactive 앵커 영상은 역할 분포와 분리한다. 동일 적의 피격 근거 등록, 반응 종료 후 TTL 변화, 기준점·범위와 대상 이동을 함께 보여준다. 시야 근거가 남아 있으면 HitReactive가 만료되어도 타깃이 유지될 수 있다.

수색과 원위치 복귀는 고정된 연속 순서가 아니다. 수색은 대상 상실과 관련된 설정, 복귀는 활동 범위 등 실제 조건에 맞게 촬영한다. 순찰 경로·Behavior Tree 노드가 해당 BP에서 실제 활성화되어 있는지는 촬영 전 확인한다.

### 디버그 도구와 보조 구현

도구 소개는 전체 옵션을 동시에 켜는 데 시간을 쓰지 않는다. Enemy 선택 → 필요한 정보 켜기 → 한 사건 발생 → 상태·이력 대조의 순서를 권장한다. `Select Outliner Focus`를 쓰면 대상을 명확히 지정할 수 있다. Player의 전투 타깃과 디버그 Focus는 구분한다.

어택 페이싱은 적용된 사례와 거리·각도 조건으로 생략된 사례를 비교한다. 방향 화살표·기준 방향·허용 범위와 Result/Reason을 함께 확인한다. 넉백은 의도 방향과 실제 변위를 확인하며 몽타주의 자세 변화와 구분한다.

소켓 회전·이동과 피드백은 일반 화면을 우선한다. 필요하면 장탈착·손 전환 전후 또는 효과 시작·종료를 느리게 재생한다. 현재 P2-A의 WeaponPresentation 진단은 부착 소켓, 전환 핸들·BlendAlpha·최근 종료 결과와 피벗 회전 정보를 제공한다. `PresentationMode`에 따라 표시 항목이 달라지며 관찰을 늦게 켜면 진행 정보가 `Progress unobserved`일 수 있다. Feedback의 VFX 생성 결과는 모든 Niagara 인스턴스의 생존 수나 실제 화면 가시성을 보증하지 않는다. 필요한 Actor 패널과 진단을 켜고 실제 출력 항목을 확인한 뒤 촬영하며, 소스 근거는 [무기·피드백 진단](../../../Source/Portfolio/Core/Debug/FWeaponPresentationDebug.cpp)을 따른다.

HUD 영상은 Player 자원 증감과 Target 변경을 분리해서 촬영한다. 샘플 값이 남은 항목은 실제 연동 성공의 근거로 사용하지 않는다. 아이템 수량·GuardBreak처럼 준비된 표시만 있는 항목은 별도 구현 결정 전 완료 범위에 포함하지 않는다.

가드 비교는 같은 에셋에서 수정 전 정리 조건을 복원한 재현이라는 점을 유지한다. 후방 피격은 사진의 시점과 로그의 공통 비교 시점을 구분한다. 인식 지연은 AI 초기화부터 첫 성공 감지 콜백까지이며 공격 시작 지연이 아니다. 집계 JSON에 기록된 측정 조건인 1600×900·60fps 제한·VSync 0·HUD/녹화 없음 조건과 회당 40초, CSV 앞뒤 3초 제외, 실행별 p95의 3회 중앙값 집계를 유지한다. 전체 프레임 시간 개선은 주장하지 않는다.

## 편집과 근거 표시

기술 챕터 하나는 다음 순서로 편집한다.

1. 입증할 내용을 한 문장으로 제시한다.
2. 실제 속도의 연속 플레이를 보여준다.
3. 같은 take의 해당 순간을 정지·확대하거나 느리게 재생한다.
4. 상태 변화 또는 원본 로그에서 필요한 2~4개 항목만 강조한다.
5. 관찰 결과와 코드로 확인한 구조를 짧게 구분한다.

정지·슬로모션은 편집 과정에서 적용하고 정상 속도도 남긴다. 게임 시간 배율을 바꾼 take는 정상 실행과 동일 조건으로 설명하지 않는다. 다른 take의 로그를 같은 사건처럼 덧붙이지 않는다. 로그 문구를 성공 메시지처럼 새로 만들지 않는다.

화면 자막은 `공격 시작`, `판정 결과: Parry`, `HP 변화 없음`, `기존 공격 종료 → Hit 시작`처럼 관찰 포인트를 안내한다. 클래스명 전체 나열은 기술 문서로 넘기고, Actor·결과 일련번호 등 사건 연결에 필요한 값은 유지한다.

## 원본 보관과 완료 기준

각 take 기록에는 다음 항목을 남긴다. 반복 촬영 번호는 영상 원본을 구분하는 기록에만 사용하며 문서 파일명에는 날짜·회차를 넣지 않는다.

```text
사례 / take 식별자:
확인할 주장 / 연결 페이지:
촬영 시각 / 시간대:
HEAD / dirty 상태 / 빌드 식별:
맵 / GameMode / Player·Enemy BP:
관련 Montage·DataAsset / 주요 설정:
Focus Actor / Event Scope / Filter / 디버그 옵션:
원본 영상 경로 / 시작·종료 타임코드:
원본 로그 경로 / 줄·시각 / Actor / ResultSerial·Session:
화면으로 확인한 결과:
로그·코드로만 확인한 내용:
부족한 근거 / 추가 촬영 여부:
게시 URL / 챕터 / 문서 링크:
```

원본 영상·원본 로그·편집본을 구분해 보관한다. 영상 URL이 준비되면 해당 PPT 페이지와 README에 연결하고, 기술 문서에는 챕터 타임스탬프와 발췌 근거를 연결한다. 로그아웃 상태에서 재생·문서 접근을 확인한다.

촬영 완료는 화면이 보기 좋은지만으로 판단하지 않는다. 주장에 대응하는 변화가 읽히고, Actor와 사건이 연결되며, 거절·시작 판단과 실제 실행을 혼동하지 않아야 한다. 부족한 경우 주장 범위를 줄이거나 해당 take만 보충한다.
