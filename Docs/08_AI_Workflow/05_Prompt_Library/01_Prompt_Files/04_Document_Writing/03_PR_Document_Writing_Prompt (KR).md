# PR Document Writing Prompt

## 1. 목적

Branch에서 해결한 문제, 변경 의도, 책임 분리, 주요 처리 흐름, 테스트 방법, 검증 결과를 PR Document로 정리한다.

이 Prompt는 변경 목록을 나열하는 것이 아니라, branch의 목적과 변경 성격을 분류하고 핵심 흐름을 선별한 뒤 리뷰어가 코드 확인 전에 변경 의미를 이해할 수 있도록 문서화한다.

---

## 2. 사용 시점

```yaml
사용 시점
-> PR 작성 전후
-> Branch 결과를 제출용 문서로 정리할 때
-> 변경 범위와 검증 상태를 함께 정리해야 할 때
-> 관련 Issue Checklist / Bug Report / Work List와 PR 결과를 연결해야 할 때
```

---

## 3. 사용 방법

대상 Branch, 변경 파일 또는 commit range, 관련 문서, 검증 결과를 제공하고 `복사용 Prompt`를 사용한다.

상단 메타, 날짜, 상태, 브랜치, 공백 같은 공통 양식은 `00_Document_Common_Format_Prompt` 기준을 따르되, PR Document 전용 세부 양식은 이 Prompt를 우선한다.

복잡한 PR은 바로 최종 문서를 쓰지 말고 `변경 성격 분류 -> 핵심 변경 축 선별 -> KR 우선 초안 작성 -> 의미 손실 지점 체크 -> 용어 등급 결정 -> 핵심 개념 선정 -> 코드 식별자 대조 -> 본문 재검토 / 압축 -> 검증 작성` 순서로 처리한다.

여기서 `용어 등급 결정`은 EN 문서 병행 운영을 뜻하지 않고, KR 우선 초안에서 의미가 흐려지는 지점만 골라 어떤 용어를 KR로 유지하고 어떤 식별자만 EN으로 병기하거나 유지할지 정하는 기준을 의미한다.

기본 작업 방식은 `초안 작성 -> 자체 검토 / 보조 검토 -> 보완 반영 -> 검증 -> 사용자 검토`까지 통합 진행한다. 사용자는 검증된 초안을 기준으로 문서 방향, 표현, 용어 선호를 조율한다.

단, PR 목적이 불명확하거나 근거 문서가 충돌하거나 구현 범위와 후속 범위가 구분되지 않거나, 핵심 용어를 임의로 정하면 의미가 바뀔 위험이 있으면 중간에 멈추고 사용자 결정을 요청한다.

---

## 4. 복사용 Prompt

````text
아래 작업을 PR Document 형식으로 작성 또는 보완해줘.

대상 작업:
- [Branch / PR / commit range / changed files]

관련 문서:
- Work List:
- Issue Checklist:
- Bug Report:
- PR Document:
- Portfolio Document:
- Verification Log:
- Code Review:

작성 목표:
- 변경 목록 나열보다 작업 의도, 책임 분리, 실행 흐름, 결과 동작을 우선 정리해줘.
- 무엇을 만들었는가보다 이번 Branch에서 어떤 기준 / 흐름 / 운영 단위가 가능해졌는지 먼저 설명해줘.
- 변경사항을 `Feature / Refactoring / Troubleshooting / Documentation / Data-Asset` 성격으로 먼저 분류해줘.
- 문서 PR이 Documentation 중심이면 `Feature / Refactoring`을 억지로 만들지 말고 Documentation 단일 카테고리로 구성해줘.
- 문서 체계 / Prompt 체계 PR에서는 기준 문서와 실제 본문을 구분해 설명해줘. 예: `Prompt Blueprint`는 제작 / 관리 기준, `Prompt Files`는 실제 작업 중 호출할 본문.
- 요약은 코드를 보지 않는 동료 개발자나 기획자도 이해할 수 있게, 전문용어를 줄이고 무엇을 왜 바꿨는지 행동 중심으로 작성해줘.
- 요약 bullet의 짧은 라벨은 본문 핵심 개념 / 변경 범위 제목과 추적 가능하도록 작성해줘.
- Feature는 새로 가능해진 실행 흐름이나 사용자 관찰 동작을, Refactoring은 그 흐름을 가능하게 한 책임 분리 / 구조 재편을 중심으로 구분해줘.
- 요약 bullet 라벨은 추상 명사형 구조명보다 실제로 무엇을 갱신 / 전달 / 전환 / 분리했는지 드러나게 작성해줘.
- `기반 마련`, `공급 분리`, `구조 정리`처럼 넓은 표현은 실제 동작을 흐리면 피하고, 필요한 경우 더 구체적인 동사로 바꿔줘.
- 요약에서 줄인 프로젝트 고유 용어는 필요한 경우 `핵심 개념` 섹션에서 따로 설명해줘.
- PR을 대표하는 핵심 변경 축 3~6개를 선별하고, 나머지 세부 구현은 필요한 섹션으로 내려줘.
- 코드의 실제 타입명 / API / struct / enum / 파일명을 확인하되, 본문은 코드 식별자 나열보다 변경 의미를 중심으로 작성해줘.
- 같은 이름의 함수 / API / 역할명이 여러 객체에 존재하면 축약하지 말고 소유 주체를 명시해줘.
- `현재`, `실행 중인`, `active` 같은 표현은 branch 코드에 실제 active 개념이나 active manager가 있을 때만 사용하고, 없으면 소유 주체나 호출 대상 객체를 명시해줘.
- 기능이 어떤 flow / lifecycle 안에서 동작하는지 설명해줘.
- 같은 용어가 이전 / 후속 PR에서 서로 다른 의미로 쓰이면 최신 의미를 소급하지 말고, 해당 PR의 branch 시점 의미를 기준으로 작성해줘.
- 같은 용어를 유지해야 한다면 `P14 기준 ReactionFeedback`처럼 branch 시점 기준을 문장 안에서 드러내줘.
- 문서 전체는 KR 설명을 우선하고, 영문 표기는 설명에 꼭 필요한 핵심 식별자에만 제한적으로 사용해줘.
- 먼저 KR 우선 초안을 작성한 뒤, KR만으로 의미가 흐려지는 지점만 `KR 유지 / KR + EN 병기 / EN 유지`로 나눠 체크해줘.
- `KR + EN 병기`로 정한 용어는 각 섹션 첫 등장에만 병기하고, 같은 섹션 안의 이후 언급은 EN 식별자만 사용해줘.
- 병기 규칙은 문서 전체에서 동일하게 적용하고, 용어별 예외 규칙은 만들지 말아줘.
- `핵심 개념`은 영문 용어 목록이 아니라, KR 설명만으로 의미가 흐려지는 핵심 식별자를 제한적으로 소개하는 섹션으로 작성해줘.
- 핵심 개념 목록 앞에는 이 PR의 핵심 관계나 처리 축을 한 문장으로 먼저 설명해줘.
- 여러 섹션에서 분기 기준으로 반복되는 값이나 결과 타입은 핵심 개념 후보로 올려줘.
- 복잡한 구조 변경 PR에서는 판단 context, 규칙, directive / result, lifecycle, cleanup 단계처럼 본문 이해에 반복적으로 필요한 단위를 핵심 개념 후보로 우선 검토해줘.
- 병기하거나 유지한 EN 식별자는 실제 코드 / 문서 / 에셋 / 브랜치명과 맞는지 대조해줘.
- 테스트 방법과 검증 결과를 분리해줘.
- 변경 범위에서 언급한 분기값 / 상태값 / 결과값은 테스트 방법 또는 검증 결과에서 최소 1회 대응해줘.
- `변경 범위` 섹션 설명문은 공통 템플릿을 그대로 쓰지 말고, 해당 PR이 어떤 책임 / 흐름 / 동작을 구성하거나 보완했는지 한 문장으로 요약해줘.
- 문서 PR의 변경 배경은 원인 / 계기 / 대략적인 방향성까지만 작성하고, 실제 산출물 목록과 폴더 구성은 변경 범위에서 다뤄줘.
- 문서 PR의 변경 범위는 작업 로그나 파일명 나열이 아니라 이번 PR이 완성한 문서 운영 기준 / 흐름 / 역할 분리 같은 의도 단위로 작성해줘.
- 실제 생성 / 정리한 문서, 기준 문서, Prompt 본문, 검증 예시는 변경 축의 근거로만 사용하고, 세부 산출물 목록은 관련 문서 / 구현 결과 / 검증 기준에서 다뤄줘.
- 검증용 예시 문서는 실제 구현 문서처럼 쓰지 말고, 어떤 흐름 확인을 위한 검증용 산출물인지 명시해줘.
- 변경 범위의 `어떻게`가 길어지면 단순 개행이 아니라 조건 / 시점 / 호출 대상 / 결과 동작 같은 의미 단위로 문장을 나눠줘.
- Actor spawn, UObject `NewObject` 생성처럼 생성 방식이 코드상 다르면 구분하되, 왜 표현을 다르게 썼는지 문장 안에서 드러나게 작성해줘.
- 검증하지 않은 항목은 `미검증 항목` 또는 `비범위`로 분리해줘.
- Bug Report가 별도로 있는 문제는 PR에서 재현 / 원인 설명을 반복하지 말고, PR에는 함께 보정한 범위만 요약해줘.
- Bug Report 연결은 PR 핵심 흐름의 직접 보완인지, 같은 PR에서 함께 처리한 안정성 / 호환성 보완인지 구분해줘.
- Bug Report가 PR 변경의 직접 근거이면 요약, 변경 범위, 관련 문서에서 같은 변경 축으로 연결하되, 재현 조건과 원인 분석은 Bug Report로 넘겨줘.
- Troubleshooting은 Bug Report가 있거나, 명확히 `문제 발생 -> 원인 / 보완 -> 결과` 흐름이 있는 경우에만 사용해줘.
- 단순 구조 보강, 기능 가능 범위 확장, 책임 분리는 Troubleshooting이 아니라 Feature 또는 Refactoring으로 분류해줘.
- 관련 문서는 `관련 문서` 작성 기준에 따라 확인 가능한 실제 파일명만 작성해줘.
- 재작성 예정이거나 매칭이 불확실한 문서는 관련 문서 항목을 만들지 말아줘.
- 현재 Branch 범위에 없던 최신 구조를 완료 내용처럼 쓰지 말아줘.
- 구현된 범위와 후속 확장 범위가 헷갈릴 때는 변경 범위 / 주요 처리 흐름 / 구현 결과 중 최소 두 곳에 제한을 명시해줘.
- 후속 작업은 못 끝낸 범위처럼 쓰지 말고, 초기 구축 이후 실사용 데이터로 다시 조정할 후보나 다음 branch에서 검토할 범위로 설명해줘.
- `v1`은 후속 범위가 명확히 분리되어 있고 현재 Branch 목표가 검증 가능하게 닫힌 경우에만 사용해줘.
- 같은 관련 문서 카테고리가 여러 개이고 역할이 다르면 `W01 Work List`, `W02 Work List`처럼 구체 라벨을 붙여줘.
- 초안 작성 중 핵심 흐름, 용어 사용 기준, 생략할 세부 구현, 섹션 적용 범위가 애매하면 후보 목록을 만들고 사용자와 조율해줘.
- 사용자가 문장 / 용어 / 섹션 역할에 대해 질문하면 즉시 수정안만 제시하지 말고, 기존 표현을 선택한 의도와 근거를 먼저 설명해줘.
- 사용자 의견은 즉시 수용하거나 반박하지 말고 `코드 사실 / 설계 의도 / 표현 선호` 중 무엇에 가까운지 먼저 분류해줘.
- 코드 사실 / Branch 시점 / API / 데이터 구조 문제는 실제 코드와 문서 근거를 기준으로 판단하고, 사용자 의견과 달라도 근거가 있으면 명확히 지적해줘.
- 설계 의도 / 문서에서 강조할 메시지 문제는 사용자가 설계자이므로 사용자 의도를 우선 존중하되, 코드 사실과 충돌하면 충돌 지점을 분리해서 설명해줘.
- 표현 / 문체 / 독자 경험 문제는 사용자 선호를 우선하되, 문서 일관성이나 독해성 문제가 있으면 대안과 근거를 함께 제시해줘.
- 사용자가 특정 문장을 반복해서 문제 삼으면 초안 문장을 더 다듬기보다, 그 문장의 설명 프레임과 핵심 동사가 잘못 잡혔는지 먼저 재검토해줘.
- 각 섹션을 수정하기 전에는 이 섹션의 핵심 동사가 무엇인지 확인해줘. 예: 제어한다, broadcast한다, binding한다, 전달한다, 검증한다, 분리한다.
- 기본적으로 초안 작성, 자체 검토, 보완 반영, 검증까지 통합 진행한 뒤 사용자 검토용 결과를 보고해줘.
- 중간에 사용자 결정이 필요하면 어느 단계까지 진행했는지, 어떤 기준에 위반되어 멈췄는지, 사용자가 결정해야 할 선택지가 무엇인지, 권장안이 무엇인지 보고해줘.
- 결과 보고 시에는 거친 단계, 각 단계에서 발견한 이슈, 반영한 대응, 남은 조율 포인트, 검증 결과를 함께 요약해줘.
- Branch closeout 단계에서는 남길 로그, 제거한 임시 로그, 현재 Branch에서 닫은 범위, 다음 Branch로 넘긴 범위, Work List 완료 상태, Prompt 반영 후보를 함께 점검해줘.

작성 프로세스:
1. 변경사항 수집: branch, commit range, diff, 관련 Issue Checklist / Bug Report / Work List를 확인한다.
   - 과거 PR 문서 재작성은 해당 branch 마지막 코드와 당시 문서 기준으로 시점을 고정한다.
   - 최신 main 또는 후속 refactor에서 생긴 용어와 구조를 완료 범위처럼 끌어오지 않는다.
   - branch 코드와 당시 문서에서 등장하는 주요 용어 후보를 모아 branch-backed 공식 용어표를 먼저 만든다.
   - 공식 용어표에는 코드 식별자, 문서 표기, 쉬운 설명, 허용 표현, 금지 표현을 포함한다.
2. 변경 성격 분류: `Feature / Refactoring / Troubleshooting / Documentation / Data-Asset`로 나눈다.
3. 핵심 변경 축 선별: PR을 대표하는 변경 3~6개만 상위 섹션으로 올린다.
4. KR 우선 초안 작성: 전문용어를 몰라도 이해할 수 있도록 행동 / 문제 / 결과 중심으로 요약과 본문 초안을 작성한다.
5. 의미 손실 지점 체크: KR만으로 코드 책임, 구조 의미, 문서 추적성이 흐려지는 지점을 찾는다.
6. 용어 등급 결정: 의미 손실 지점만 `KR 유지 / KR + EN 병기 / EN 유지`로 나눈다.
7. 핵심 개념 선정: KR 설명만으로 의미가 흐려지는 핵심 식별자만 제한적으로 정의한다.
8. 코드 식별자 대조: 병기하거나 유지한 EN 식별자가 실제 코드 / 문서 / 에셋 / 브랜치명과 맞는지 확인한다.
9. 본문 재검토 / 압축: 핵심 흐름, 용어, 생략 범위, 과한 설명 여부를 조율하고 반복 설명과 심볼 나열을 제거한다.
   - 초안 문장이 이미 있더라도 그대로 신뢰하지 않고, 사용자 지적이 반복되는 문장은 설명 프레임 자체를 재검토한다.
   - 섹션별 핵심 동사와 구현 동사가 맞는지 확인한다.
   - Feature는 동작, Refactoring은 책임 위치 / 연결 지점 / 범위 분리로 분리하고 같은 구현을 반복하지 않는다.
10. 검증 작성: 테스트 방법, 검증 결과, 미검증 / 후속 작업, 관련 문서를 정리한다.
   - Work List에 명시된 검증 기준이 있으면 PR의 테스트 방법 / 검증 결과와 대조해 누락 여부를 확인한다.
   - Work List에는 있는데 PR 검증 결과에 빠진 항목은 자체 검토 Finding으로 잡거나, 미검증 / 비범위로 명시한다.
   - PIE 검증은 단순 실행 여부보다 outcome / commit / state / reaction / feedback / packet 흐름이 확인됐는지 대조한다.
11. 자체 검토 / 보조 검토: 양식 일관성, 근거 정합성, 독자 관점 가독성을 독립적으로 점검한다.
   - 검토 결과를 사용자에게 Finding으로 제시할 때는 `### Finding N. 제목` 단위로 나누고, `Severity / 위치 / 문제 / 권장 수정`을 분리한다.
   - Finding 사이에는 `---`를 넣어 권장 수정 bullet과 다음 Finding 제목이 시각적으로 섞이지 않게 한다.
12. 보완 반영: 검토 결과 중 타당한 항목만 선별해 문서에 반영하고 과한 확장이나 근거 없는 표현은 제외한다.
13. 최종 검증: 문체, 용어 병기, 관련 문서 파일명, 공백, `git diff --check`를 확인한다.
14. 결과 보고: 단계별 이슈와 대응, 남은 조율 포인트, 검증 결과를 사용자에게 보고한다.

프롬프트 동기화 운영 기준:
- 작업 중 프롬프트와 다른 최신 문서 패턴을 적용한 경우 결과 보고에 명시한다.
````

## 5. 작성 기준

```yaml
용어 처리
-> 먼저 KR 우선 초안을 작성하고, KR만으로 의미가 흐려지는 지점만 용어 등급 후보로 올림
-> 과거 PR 문서는 branch-backed 공식 용어표를 기준으로 용어를 고정하고, 후속 PR에서 생긴 최신 용어를 현재 PR의 완료 개념처럼 사용하지 않음
-> 공식 용어표는 나온 표현을 모두 보관하는 목록이 아니라, 이 문서에서 사용할 canonical term과 금지 표현을 정하는 기준임
-> 공식 용어표 항목은 `코드 식별자 / 문서 표기 / 쉬운 설명 / 허용 표현 / 금지 표현`으로 정리함
-> 문서 작성 중 정의되지 않은 용어가 새로 등장하면 문장을 방어하지 않고, 코드 기준과 공식 용어표를 다시 확인해 유지 / 교체 / 제거를 결정함
-> 동일 함수명 / 동일 역할명이 여러 객체에 있으면 소유 주체를 포함해 표기함. 예: `UCWeaponComponent::PlayAction()`과 action instance의 `PlayAction()`을 구분
-> `현재 action`, `실행 중인 action`, `active reaction` 같은 표현은 실제 코드에 active 개념이 있을 때만 사용하고, 단일 소유 객체만 있으면 `UCWeaponComponent가 소유한 action instance`처럼 작성
-> KR 유지: KR만으로 의미가 충분히 전달되는 행동 / 상태 / 목적 / 결과
-> KR + EN 병기: KR 설명만으로 코드 또는 문서 추적성이 떨어지는 핵심 프로젝트 용어
-> EN 유지: 코드 식별자, enum value, branch / file / document name처럼 정확한 식별이 필요한 값
-> KR + EN 병기 용어는 각 섹션 첫 등장에만 병기하고, 같은 섹션 안의 이후 언급은 EN 식별자만 사용
-> 병기 규칙에는 용어별 예외를 두지 않음
-> H2 / H3 제목에 EN 식별자가 들어갈 때는 병기하지 않고 EN만 사용하며, 해당 섹션 본문 첫 등장에 병기
-> 핵심 개념에는 KR 설명만으로 의미가 흐려지는 핵심 식별자만 포함
-> 병기하거나 유지한 EN 식별자는 실제 코드 / 문서 / 에셋 / 브랜치명과 대조
-> 애매한 경우 후보 목록을 만들어 사용자와 조율
```

```yaml
작성 양식
-> EN 표기 / 소대문자 / 인라인 코드 기준은 `00_Document_Common_Format_Prompt`를 따른다.
-> H2 바로 아래에는 필요한 경우 섹션 의도를 한 문장으로 작성
-> 섹션 의도 문장은 공통 템플릿을 그대로 반복하지 않고, 해당 PR의 성격에 맞춰 구체화
-> 변경 범위는 `- **왜**:`, `- **어떻게**:`, `- **결과**:` 형식을 기본으로 사용
-> 섹션을 수정하기 전에는 해당 섹션의 핵심 동사를 먼저 확인
-> 핵심 동사가 `broadcast`, `binding`, `전달`, `검증`, `제어`, `분리`처럼 코드 동작에 가까운 경우 추상적인 `정리`, `구성`, `경계`로 흐리지 않음
-> 최상위 bullet 사이에는 빈 줄을 둠
-> 하위 bullet에는 강제 빈 줄을 넣지 않음
-> 같은 층위의 항목은 제목 문법, 추상화 수준, 서술 구조를 맞춤
-> Action / Reaction, Player / AI처럼 대응되는 구조를 함께 설명할 때는 가능한 같은 문장 구조로 작성
-> 실제 코드 식별자 / 에셋명 / key / enum 값 / 파일명은 인라인 코드로 감쌈
-> 핵심 개념으로 정의한 EN 용어라도 개념명으로 읽히는 경우에는 인라인 코드를 쓰지 않음
-> 문서상 축약한 개념명이나 역할명은 실제 코드 식별자가 아니면 인라인 코드로 감싸지 않음
-> 코드 추적성이 필요한 경우에는 축약명 대신 정확한 코드 식별자를 사용
-> PR에서 정의한 핵심 개념명은 공통 양식 기준에 따라 대문자 시작 표기를 유지
-> PR의 H2 / H3 제목과 요약 bullet 라벨에서도 일반 EN 용어는 소문자로 작성하고, 핵심 개념명만 대문자 시작 표기를 유지
-> 제목 안의 EN 표현은 일반 설명어인지 핵심 개념명인지 확인하고, 핵심 개념명이면 문서 전체 표기를 통일
-> 같은 내용을 요약 / 변경 범위 / 구현 결과 / 정리에서 반복하지 않음
```

```yaml
요약
-> 핵심 개념보다 먼저 읽히므로, 전문용어를 몰라도 PR 목적과 변경 의미를 이해할 수 있어야 함
-> PR의 변경 성격과 핵심 결과를 빠르게 파악할 수 있도록 작성
-> `Feature / Refactoring / Troubleshooting / Documentation / Data-Asset` 성격별로 핵심 변경만 압축
-> 문서 PR이 Documentation 중심이면 `핵심 변경은 다음과 같다`처럼 단일 성격에 맞는 안내 문장을 사용하고, `성격별 핵심 변경` 표현을 억지로 쓰지 않음
-> 문서 체계 / Prompt 체계 PR은 첫 문장에서 목적과 결과가 함께 드러나게 작성. 예: `본 PR은 ... 문서 구조와 ... 초안을 구성한 작업이다`
-> 문서 PR 요약에서는 상위 문서 묶음의 역할과 하위 문서의 역할을 구분해 쓰고, 같은 분리 / 구성 설명을 반복하지 않음
-> 프로젝트 내부 용어와 코드 식별자를 최소화하고, 행동 / 문제 / 결과 중심으로 작성
-> 핵심 개념에서 아직 설명하지 않은 프로젝트 내부 용어는 먼저 남발하지 않고, 독자가 이해할 수 있는 일반 표현으로 풀어씀
-> 내부 처리 단계명이나 구조 용어가 중요하더라도 요약에서는 먼저 쉬운 역할 설명으로 풀고, 핵심 개념 이후에 정의함
-> 내부 용어가 꼭 필요하면 쉬운 설명 뒤 괄호로 보조 표기
-> 각 성격별 bullet은 `**짧은 라벨**: 행동 중심 설명` 형식으로 작성
-> bullet 라벨은 본문 핵심 개념 또는 변경 범위 제목과 추적 가능하도록 작성
-> bullet 라벨도 추상 명사형보다 갱신 / 전달 / 전환 / 분리 / 연결 / 복구처럼 실제 동작이 드러나는 표현을 우선
-> `기반 마련`, `공급 분리`, `구조 정리`처럼 범위가 넓은 표현은 문장 안에서 무엇을 마련 / 분리 / 정리했는지 바로 드러나지 않으면 사용하지 않음
-> Feature는 새로 가능해진 실행 흐름 / 관찰 가능한 동작을 중심으로 작성
-> Refactoring은 그 흐름을 가능하게 한 책임 분리 / 구조 재편을 중심으로 작성
-> Feature와 Refactoring이 같은 구현을 반복하면 Feature는 새 동작, Refactoring은 책임 위치 / 연결 지점 / 범위 분리로 역할을 나눔
-> Troubleshooting은 무엇이 잘못될 수 있었는지와 어떻게 보완했는지가 드러나게 작성
-> 기능 흐름을 닫거나 검증한 안정화 작업은 명확한 문제-원인-보완 흐름이 없으면 Feature / Refactoring 안에서 설명
-> Bug Report가 없고 명확한 문제-원인-보완 흐름이 없다면 Troubleshooting 섹션을 만들지 않음
-> Bug Report가 담당하는 재현 조건과 원인 분석을 반복하지 않음
```

```yaml

-> 프로젝트 고유 용어는 일반 영어 뜻보다 해당 프로젝트 안의 역할, 판단 기준, 실행 책임이 더 중요한 이름을 말함
-> 목록 앞에는 이 PR의 핵심 관계나 처리 축을 한 문장으로 먼저 설명
-> 여러 섹션에서 분기 기준으로 반복되는 값 / 결과 타입 / 상태값은 핵심 개념 후보로 검토
-> 복잡한 구조 변경 PR에서는 판단 context, 규칙, directive / result, lifecycle, cleanup 단계처럼 본문 이해에 반복적으로 필요한 단위를 핵심 개념 후보로 검토
-> 같은 용어가 branch 시점에 따라 의미가 달라지면, 핵심 개념이나 본문에서 해당 PR 기준 의미를 명시
-> 핵심 개념 이후에도 KR 설명을 우선하고, 정의한 식별자는 행동과 책임 설명을 보조할 때만 사용
-> 핵심 개념에 없는 EN 용어는 본문에서 되도록 풀어씀
```

```yaml
변경 배경
-> 이번 PR이 필요했던 이유와 기존 구조의 문제를 정리
-> 변경 범위의 `왜`와 논리 흐름이 이어지도록 작성
-> 변경 배경은 변경 범위에서 발생한 변화의 배경을 더 넓게 설명하는 섹션으로 보고, payload 목록이나 함수 호출 순서 같은 구현 상세를 쓰지 않음
-> 문서 체계 / 운영 체계 PR에서는 문제 제기 뒤에 대략적인 구성 방향까지 제시할 수 있음
-> 단, 구체 산출물 목록과 파일 / 폴더 구성은 변경 범위에서 다루고, 변경 배경에서는 원인 / 계기 / 방향성까지만 작성
-> 사용자가 특정 배경 문단을 계속 문제 삼으면 문장 표현보다 설명 프레임이 변경 범위의 `왜`와 어긋났는지 먼저 검토
-> 새로운 문제를 끼워 넣지 않고 branch에서 실제로 다룬 배경만 작성
```

```yaml
변경 범위
-> PR을 대표하는 변경 축 3~6개를 하위 섹션으로 작성
-> 각 변경 축은 `왜 / 어떻게 / 결과` 형식을 기본으로 작성
-> 변경 범위 H2 아래 설명문은 해당 PR의 변경 범위를 한 문장으로 요약하고, "문제를 어떻게 고쳤다" 같은 기본 문구를 모든 PR에 반복하지 않음
-> `왜`는 변경 배경의 문제를 해당 변경 항목 관점에서 이어받아 작성
-> `어떻게`는 실제 설정 위치, 책임 이동, 구조 변경 방식을 설명
-> 문서 PR의 `변경 범위`는 실제 생성 / 정리한 파일 목록보다 이번 PR이 완성한 문서 운영 기준 / 흐름 / 역할 분리 같은 의도 단위로 구체화
-> 파일명 / Prompt명 / Index명 / 검증 예시는 변경 축의 근거로만 사용하고, 변경 범위 전체가 세부 산출물 나열이 되지 않게 함
-> 작업 중 생긴 `draft`, `comparison`, 중간 audit, finding draft 같은 임시 산출물은 변경 필요성의 근거로 쓰지 않음
-> 임시 산출물이 필요하면 `어떻게`의 검토 방식이나 `결과`의 정리 대상으로만 제한해 설명
-> 문서 / Prompt 체계 PR에서 `Prompt Blueprint`는 제작 / 관리 기준 문서, `Prompt Files`는 실제 작업 중 호출할 본문으로 구분해 설명
-> 검증용 예시 문서가 있으면 실제 구현 문서처럼 쓰지 않고, 어떤 흐름 확인을 위한 검증용 산출물인지 명시
-> `어떻게`가 길어지면 문장 하나에 여러 구현 동작을 묶지 않고 조건 / 시점 / 호출 대상 / 결과 동작 단위로 분리
-> 단순히 빈 줄을 넣는 것이 아니라 문장 자체를 짧은 의미 단위로 나눔
-> runtime parameter나 state 값을 설명할 때는 "결과"로 뭉뚱그리지 않고 현재 상태 값 / runtime 값 / animation parameter처럼 실제 의미에 맞춰 표현
-> AnimBP / state machine / BlendSpace 설명은 구조 라벨만 나열하지 않고, 어떤 값이 바뀌면 어떤 animation이나 state로 전환되는지 동작으로 풀어씀
-> 생성 방식이 서로 다른 객체를 함께 설명할 때는 코드 사실을 유지함. 예: actor는 spawn, UObject는 `NewObject`로 생성
-> 생성 방식 차이를 남길 경우 `actor인 X`, `UObject인 Y`처럼 차이가 왜 필요한지 독자가 알 수 있게 작성
-> `결과`는 동작, 해석, 책임 경계가 어떻게 달라졌는지 작성
-> `왜`에는 구현 payload 목록을 쓰지 않고, 해당 변경이 필요한 이유와 흐름 단절을 작성
-> `어떻게`에는 코드 기준 실제 동작을 작성하되, delegate event라면 `broadcast`, 연결이라면 `binding`처럼 실제 구현 동사를 사용
-> `결과`는 데이터가 정리되었다는 설명보다 어떤 동작 경로가 가능해졌는지 작성
-> 코드 변경 목록보다 구조 변화와 결과를 우선 설명
-> 실행 책임과 요청 구성 / 전달 책임을 구분
-> 어떤 component가 request를 만들고 다른 subsystem / player-local 경로 / executor가 실제 실행한다면 해당 component가 직접 실행한다고 쓰지 않음
-> 이 경우 `구성한다`, `전달한다`, `요청한다`, `dispatch한다`처럼 위임 관계가 드러나는 표현을 사용
-> notify가 직접 처리하지 않고 signal이나 request만 만드는 경우 `처리한다`로 쓰지 않고 `signal을 전달한다`, `request를 만든다`, `task / component에 위임한다`처럼 작성
-> feedback 계열 변경은 request 생성 / 전달 / 실제 실행 주체를 구분하고, player-local feedback처럼 별도 경로가 있으면 실행 주체를 단정하지 않음
-> 대응 구조의 변경 축은 같은 책임 흐름으로 비교되도록 작성하되, 구현상 차이가 있는 경우 그 차이를 명시
-> sender / receiver, attacker / defender처럼 양쪽 책임이 나뉘는 구조는 한쪽만 과하게 상세하게 쓰지 않고 같은 밀도로 설명
```

```yaml
주요 처리 흐름
-> PR 결과로 달라진 핵심 판단 / 실행 / 정리 흐름을 작성

```


## 10. 모호성 처리 기준

```yaml
모호한 경우
-> Branch 시점과 현재 최신 구조를 분리
-> 같은 용어가 후속 PR에서 의미가 달라졌다면 해당 PR 시점의 의미를 기준으로 쓰고, 필요할 때만 후속 변화로 구분

-> 사용자가 문장 / 용어 / 섹션 역할에 대해 질문하면 먼저 기존 표현을 선택한 의도, 근거가 된 코드 / 문서 / 초안 / 기존 패턴, 그 의도로 인해 선택한 작업 방식을 설명
-> 그다음 사용자 지적을 어떤 문제로 이해했는지, 기존 의도와 어디서 갈렸는지, 유지 / 수정 / 재프레이밍 중 어떤 판단을 하는지 설명
-> 사용자 의견은 코드 사실 / 설계 의도 / 표현 선호 중 무엇에 가까운지 먼저 분류
-> 코드 사실 / Branch 시점 / API / 데이터 구조 문제는 실제 코드와 문서 근거를 기준으로 판단하고, 사용자 의견과 달라도 근거가 있으면 명확히 지적
-> 설계 의도 / 문서에서 강조할 메시지 문제는 사용자가 설계자이므로 사용자 의도를 우선 존중하되, 코드 사실과 충돌하면 충돌 지점을 분리해서 설명
-> 표현 / 문체 / 독자 경험 문제는 사용자 선호를 우선하되, 문서 일관성이나 독해성 문제가 있으면 대안과 근거를 함께 제시
-> 초안 문장이 있어도 사용자가 같은 문장에 반복적으로 문제를 제기하면 초안의 설명 프레임 자체가 틀렸는지 먼저 재검토
-> 사용자가 특정 용어에 대해 "이게 뭐냐"거나 "왜 이 용어를 쓰냐"고 물으면 단순 설명 요청으로만 보지 않고 용어 모델 흔들림 여부를 먼저 확인
-> 해당 용어가 branch 코드에 있는지, 문서 앞에서 정의했는지, 같은 개념을 다른 말로 부르고 있지 않은지, 후속 PR 용어가 섞였는지 점검
-> 같은 함수명이나 역할명이 서로 다른 객체에 있을 때는 어떤 객체의 API인지 먼저 확인하고, 문서에서는 소유 주체를 생략하지 않음
-> `현재` / `실행 중인` / `active` 표현이 실제 코드 구조보다 강한 의미를 만들면 소유 관계나 호출 관계 표현으로 바꿈
-> 용어 모델이 흔들렸다면 문장 단위 수정이 아니라 공식 용어표 재고정 단계로 전환
-> PR 성격 분류가 애매하면 후보를 제시하고 사용자와 조율
-> 용어 사용 기준이 애매하면 `KR 유지 / KR + EN 병기 / EN 유지` 후보를 제시
-> 핵심 변경 축이 많으면 대표 3~6개 후보를 제시하고 사용자와 조율
-> 관련 문서 번호를 자동 가정하지 않음
-> 파일명 매핑이 불확실하면 항목을 만들지 않음
-> 확인 불가 항목은 미검증 / 비범위 / 리뷰 포인트로 분리
```

## 11. 검증 기준

```yaml
검증 기준
-> Work List 또는 Issue Checklist 목표와 PR 결과가 연결되는가
-> PR 성격별 요약이 변경 범위와 연결되는가
-> 과거 PR 문서는 branch 시점이 고정되었고, 후속 refactor 용어가 완료 범위처럼 섞이지 않았는가
-> 같은 용어가 branch 시점별로 다른 의미를 가지면 해당 PR 기준 의미가 문서에 드러나는가
-> 공식 용어표에서 정한 문서 표기와 금지 표현이 요약 / 핵심 개념 / 변경 배경 / 변경 범위 / 주요 처리 흐름 / 구현 결과 / 테스트에 일관되게 적용되었는가
-> 같은 이름의 함수 / API가 여러 객체에 있을 때 소유 주체가 명확히 쓰였는가
-> `현재`, `실행 중인`, `active` 표현이 branch 코드의 실제 개념보다 과하게 쓰이지 않았는가
-> 주요 처리 흐름 안의 모든 용어가 branch 코드 또는 앞선 핵심 개념 / 공식 용어표에서 확인되는가
-> 문서 전체가 KR 설명 우선으로 작성되었는가
-> KR 초안에서 의미가 흐려지는 지점만 EN 병기 / 유지 후보로 올렸는가
-> 핵심 개념에 KR 설명만으로 의미가 흐려지는 핵심 식별자만 포함되었는가
-> EN 용어가 코드 식별 또는 설명상 필요한 곳에만 제한적으로 사용되었는가
-> 코드 식별자 / 핵심 개념명 / 일반 EN 용어의 소대문자와 인라인 코드 표기가 공통 양식 기준과 일치하는가
-> 병기하거나 유지한 EN 식별자가 실제 코드 / 문서 / 에셋 / 브랜치명과 일치하는가
-> 변경 배경의 문제와 변경 범위의 `왜`가 일관되는가
-> 변경 범위가 `왜 / 어떻게 / 결과`로 정리되었는가
-> 변경 범위 H2 설명문이 공통 템플릿 반복이 아니라 해당 PR의 책임 / 흐름 / 동작을 요약하는가
-> `어떻게` 문장이 조건 / 시점 / 호출 대상 / 결과 동작을 과하게 한 문장에 묶고 있지 않은가
-> 생성 방식 차이를 표현할 때 actor spawn / UObject 생성처럼 코드 사실과 표현 이유가 함께 드러나는가
-> 각 섹션의 핵심 동사와 실제 코드 동작이 맞는가
-> 요약 bullet 라벨과 변경 범위 제목이 추상 명사형에 그치지 않고 실제 동작을 드러내는가
-> runtime parameter / state 값을 "결과"처럼 넓게 뭉뚱그리지 않고 실제 의미에 맞춰 표현했는가
-> AnimBP / state machine / BlendSpace 설명이 라벨 나열이 아니라 값 변화와 animation 전환 동작으로 설명되는가
-> Feature와 Refactoring이 같은 구현을 반복하지 않고, 동작 / 책임 위치 / 범위 분리로 역할이 나뉘는가
-> 변경 배경에 payload 목록이나 함수 호출 순서 같은 구현 상세가 들어가 있지 않은가
-> 사용자가 지적한 문장에 대해 기존 의도와 근거, 사용자 지적 후 재판단이 명시되었는가
-> 양쪽 책임이 나뉘는 구조에서 각 책임의 설명 밀도와 결과 기준이 균형 있게 작성되었는가
-> 주요 처리 흐름이 분기 / 순서 중심으로 압축되었는가
-> 구현 결과가 변경 범위와 중복되지 않고 최종 동작을 정리하는가
-> 변경 범위와 검증 결과가 일치하는가
-> Work List의 검증 기준이 PR의 테스트 방법 / 검증 결과에서 누락되지 않았는가
-> 테스트 방법과 검증 결과가 분리되어 있는가
-> Bug Report가 직접 근거인 경우 PR 본문은 변경 축만 요약하고 재현 / 원인 분석을 반복하지 않는가
-> 미검증 항목이 완료처럼 작성되지 않았는가
-> 관련 문서가 확인 가능한 파일명 기준으로 작성되어 있는가
-> Bug Report가 있는 문제를 PR 본문에서 과하게 반복하지 않았는가
-> git diff --check를 통과하는가
```
