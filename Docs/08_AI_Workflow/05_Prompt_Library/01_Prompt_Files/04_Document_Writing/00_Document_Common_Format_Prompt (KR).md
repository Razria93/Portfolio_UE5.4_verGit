# Document Common Format Prompt

## 1. 목적

문서 작성 시 공통으로 적용할 파일명, 상단 메타 섹션, 본문 제목, 상태값, 브랜치 표기, 문체, 공백, Markdown 구조 기준을 정의한다.

이 Prompt는 특정 문서 타입의 내용 구조를 정하는 Prompt가 아니라, 모든 Markdown 문서에 공통으로 적용할 기본 양식 기준을 제공한다.

문서 타입별 Prompt가 더 구체적인 파일명, 상단 메타, 상태값, 관련 문서 표기 기준을 제공하는 경우에는 문서 타입별 Prompt를 우선한다.

---

## 2. 사용 시점

```yaml
사용 시점
-> 새 문서를 작성하기 전 공통 양식 기준을 확인할 때
-> PR / Issue / Bug Report / System Architecture 등 문서 타입별 Prompt를 사용하기 전
-> 파일명 / 본문 제목 / 날짜 / 상태 / 브랜치 표기 기준을 통일할 때
-> 문체와 공백 규칙을 공통 기준으로 맞출 때
```

---

## 3. 사용 방법

문서 작성 Prompt와 함께 사용한다.

공통 양식은 이 Prompt를 기준으로 적용하고, 문서 타입별 섹션 구성과 내용 전개 방식은 각 문서 작성 Prompt를 따른다.

## 4. 복사용 Prompt

````text
다음 Markdown 문서를 공통 문서 양식 기준에 맞춰 작성하거나 정리해줘.

대상 문서 타입:
- [Issue Checklist / Bug Report / Pull Request / System Architecture / Technical Summary 등 입력]

대상 경로:
- [문서 / 폴더 경로 입력]

작성 또는 수정 목적:
- [작성 목적 / 수정 목적 입력]

수정 허용 범위:
- [검토만 / 직접 수정까지 허용 / 특정 항목만 수정 등 입력]

## 1. 공통 파일명 기준

- 파일명은 문서 카테고리의 기존 naming convention을 따른다.
- 신규 문서 파일명에는 언어 suffix를 붙이지 않는다.
- 기존 문서 파일명에 언어 suffix가 남아 있는 경우, 파일명 정리 작업에서 별도 제거 대상으로 다룬다.
- 파일명과 본문 문서 ID가 충돌하지 않게 한다.
- 파일명 변경이 필요한 경우 내부 참조와 index 갱신 필요 여부를 함께 보고한다.
- 문서 타입별 Prompt가 신규 파일명 규칙을 별도로 제공하면 해당 Prompt를 우선한다.

## 2. 상단 메타 섹션 기준

문서 타입별 Prompt가 별도 기준을 제공하지 않는 경우, 상단 메타 섹션은 다음 흐름을 기본으로 한다.

```md
# 문서 제목 또는 문서 카테고리명

## 제목

문서 ID: 문서 제목

---

## 목적

문서 목적을 작성한다.

---

## 관련 브랜치

- `feature/example-branch`

---
```

### 제목

- 본문 제목은 파일명 또는 문서 ID와 일치시킨다.
- 문서 ID가 있는 문서군은 `Dxx`, `Pxx`, `Bxx`, `Sxx`, `PFxx` 기준을 유지한다.
- 제목에 gitmoji, issue 번호, milestone 번호가 필요한 문서 타입인지 확인한다.
- PR 문서처럼 GitHub 게시 제목을 포함해야 하는 문서 타입은 해당 문서 작성 Prompt를 우선한다.

### 날짜

- 날짜 섹션이 필요한 문서 타입에서만 작성한다.
- 날짜는 기존 문서군 convention을 따른다.
- 날짜가 확인되지 않으면 임의 추정하지 않는다.

### 상태

- 상태 섹션이 필요한 문서 타입에서만 작성한다.
- 상태값은 기존 문서군 convention을 따른다.
- 완료 여부를 코드나 문서 근거 없이 임의 판정하지 않는다.

### 브랜치

- 브랜치 섹션이 필요한 문서 타입에서는 bullet list로 작성한다.
- 브랜치 값은 인라인 코드로 작성한다.
- 브랜치가 확인되지 않으면 `추가요망` 또는 후속 검토 항목으로 남긴다.
- 브랜치명은 `feature/...`처럼 실제 branch naming convention을 우선한다.

## 3. 문체 기준

- 제출용 / 포트폴리오용 기술 문서는 간결한 설명체를 사용한다.
- 프로젝트 내부 기술 문서와 architecture 문서는 `~함` 체를 기본으로 한다.
- PR / Bug Report / Issue Checklist는 해당 문서 작성 Prompt의 문체 기준을 따른다.
- 같은 문서 안에서 `~함`, `~했다`, `~한다`가 불필요하게 섞이지 않게 한다.
- 단순 감상, 과한 자기평가, 불필요한 변명형 문장은 제거한다.

## 4. 용어 기준

- 코드 타입, 함수, enum, struct, component 이름은 실제 코드 표기를 유지한다.
- 설계 용어는 문서군에서 이미 사용하는 공식 용어를 우선한다.
- KR / EN 혼용은 의도적으로 유지할 용어만 허용한다.
- EN 문서 병행 운영을 전제로 하지 않는다.
- 같은 문서 안에서 같은 개념을 다른 이름으로 바꾸지 않는다.
- 과거 브랜치 문서에서는 당시 용어를 유지하되, 후속 구조와 충돌할 경우 별도 안내 섹션에서 설명한다.

### EN 표기 / 소대문자 기준

- 코드 식별자, 파일명, 브랜치명, enum value, asset name은 실제 표기를 유지하고 인라인 코드로 작성한다.
- 문서에서 정의한 핵심 개념명은 대문자 시작 표기를 유지한다.
- 코드 식별자나 핵심 개념명이 아닌 일반 EN 용어는 문서 위치와 관계없이 소문자로 작성한다.
- H2 / H3 제목, bullet 라벨, 코드블럭 흐름의 첫 단어라는 이유만으로 일반 EN 용어를 대문자로 바꾸지 않는다.
- 한국어 문장 안에 포함된 일반 EN 용어도 문장 위치와 관계없이 소문자로 작성한다.
- 문서 타입별 Prompt가 특정 용어를 핵심 개념명으로 정의한 경우에만 해당 용어의 대문자 시작 표기를 허용한다.
- 핵심 개념명과 일반 EN 용어가 섞일 수 있는 경우, 첫 등장 지점에서 핵심 개념 여부를 명확히 한다.

## 5. Markdown 구조 기준

- 상단 메타 섹션의 H2 번호 여부는 문서 타입별 Prompt를 따른다.
- 본문 H2에는 문서 전체 흐름을 나타내는 번호를 붙인다.
- H3에는 같은 H2 내부에서 여러 항목이 병렬로 있을 때 `### 1) ...` 형식을 사용한다.
- H3 이하에서는 불필요한 숫자 인덱스를 남발하지 않는다.
- 선후관계가 중요한 경우에만 A / B / C 또는 1 / 2 / 3을 사용한다.
- 긴 구조, flow, responsibility list는 `yaml` 코드블럭으로 정리한다.
- 설명 문장은 코드블럭 밖에서 짧게 보완한다.

## 6. 공백 / 구분선 기준

- 주요 H2 섹션 사이에는 `---` 구분선을 사용한다.
- 헤더와 본문 사이에는 한 줄 공백을 둔다.
- 리스트 항목 사이에 불필요한 빈 줄을 넣지 않는다.
- 코드블럭 전후에는 한 줄 공백을 둔다.
- 문서 끝에는 하나의 마지막 구분선만 둔다.

## 7. 검증 기준

작성 또는 수정 후 다음을 확인한다.

- 파일명과 본문 문서 ID가 충돌하지 않는다.
- 상단 메타 섹션 순서가 문서 타입 기준과 맞다.
- 브랜치 표기가 실제 branch naming convention과 맞다.
- 문체가 문서 타입 기준과 일치한다.
- 같은 개념의 용어가 문서 안에서 흔들리지 않는다.
- 코드 식별자 / 핵심 개념명 / 일반 EN 용어의 소대문자와 인라인 코드 표기가 일관적이다.
- 상단 메타와 본문 H2 / H3 인덱스 규칙이 문서 타입 기준과 맞다.
- 코드블럭과 평문 역할이 구분된다.
- 불필요한 빈 줄과 trailing whitespace가 없다.
- `git diff --check`를 통과한다.

## 8. 결과 보고

다음 형식으로 결과를 요약한다.

1. 적용한 공통 양식 기준
2. 수정한 문서 수
3. 문서 타입별 Prompt와 충돌한 항목
4. 추가요망 또는 후속 검토 항목
5. 검증 결과

제약 조건:
- 문서 의미를 임의로 새로 만들지 않는다.
- 날짜, 상태, 브랜치를 근거 없이 추정하지 않는다.
- 과거 브랜치 문서의 당시 용어를 최신 용어로 무리하게 치환하지 않는다.
- EN 문서 병행 운영을 전제로 한 섹션이나 검증 항목을 새로 만들지 않는다.
- 검토만 요청받은 경우 직접 수정하지 않는다.
````

## 5. 입력 기준

```yaml
입력 기준
-> 대상 문서 또는 폴더 경로
-> 문서 타입
-> 작성 또는 수정 목적
-> 수정 허용 범위
-> 기준으로 삼을 문서 또는 Prompt
```

## 6. 출력 기준

```yaml
출력 기준
-> 적용한 공통 양식 기준
-> 수정한 문서 수
-> 문서 타입별 Prompt와 충돌한 항목
-> 추가요망 / 후속 검토 항목
-> 검증 결과
```

## 7. 범위 / 비범위

```yaml
범위
-> 파일명 / 본문 제목 / 상단 메타 섹션 기준
-> 날짜 / 상태 / 브랜치 표기 기준
-> 문체 / 용어 / Markdown 구조 기준
-> 공백 / 구분선 / 코드블럭 기준
-> 신규 문서 파일명 언어 suffix 미사용 기준

비범위
-> 문서 타입별 세부 내용 작성
-> 코드 구현 검토
-> 완료 여부 임의 판정
-> 날짜 / 브랜치 임의 추정
-> 기존 Prompt 파일명의 언어 suffix 일괄 제거
-> EN 문서 삭제 / archive 처리
```

## 8. 역할 경계

```yaml
Document Common Format Prompt
-> 모든 문서에 공통으로 적용할 양식 기준

Document Type Writing Prompt
-> 문서 타입별 목적, 섹션 구성, 내용 전개 기준

Document Format Review Prompt
-> 작성된 문서를 공통 양식과 문서 타입별 규칙 기준으로 단계 검토

Document Set Audit Prompt
-> 여러 문서가 하나의 문서군으로 운영 가능한지 감사
```
