# Bug Report Writing Prompt

## 1. 목적

재현 조건, 영향 범위, 기대 결과, 실제 결과, 원인, 수정, 검증 결과, 회귀 방지 기준을 Bug Report로 정리한다.

이 Prompt의 전용 책임은 개별 버그의 영향 범위, 발생 조건, 재현 방법, 기대 결과 / 실제 결과, 원인, 수정, 수정 기준, 검증 결과, 회귀 방지 기준을 분리하는 것이다.

---

## 2. 사용 시점

```yaml
사용 시점
-> 재현 가능한 문제가 발생했을 때
-> 버그 수정 결과를 문서로 남겨야 할 때
-> 원인과 수정, 검증 결과를 연결해야 할 때
```

---

## 3. 사용 방법

대상 문제, 재현 조건, 관련 코드 / 문서, 수정 결과, 검증 결과를 제공하고 `복사용 Prompt`를 사용한다.

상단 메타, 날짜, 상태, 브랜치, 공백 같은 공통 양식은 `00_Document_Common_Format_Prompt` 기준을 따르되, Bug Report 전용 세부 양식은 이 Prompt를 우선한다.

---

## 4. 복사용 Prompt

````text
아래 문제를 Bug Report 형식으로 작성 또는 보완해줘.

대상 문제:
- [증상 / 문서 경로 / issue]

관련 문서:
- Work List:
- Issue Checklist:
- Bug Report:
- PR Document:
- Portfolio Technical Document:
- Verification Log:

작성 목표:
- 신규 Bug Report 파일명은 `B##_UE5_Portfolio_Bug_Report.md`로 작성하고 `(KR)`을 붙이지 말아줘.
- 상단 메타는 `제목 / 날짜 / 상태 / 브랜치` 형식으로 작성해줘.
- 상태는 `- [ ] **진행중**` 또는 `- [x] **완료**`로 작성해줘.
- 브랜치는 bullet list로 작성하고 브랜치 값은 인라인 코드로 작성해줘.
- `유형` 또는 `Type` 섹션은 만들지 말아줘.
- `환경` 섹션 내부 항목명은 KR 기준으로 작성해줘.
- `요약 / 영향 범위 / 환경 / 발생 조건 / 재현 방법 / 기대 결과 vs 실제 결과 / 원인 / 수정 / 수정 기준 / 검증 결과 / 회귀 방지 기준 / 관련 PR / 문서 / 비고` 순서로 작성해줘.
- `영향 범위`는 문장형 반복보다 영향 대상 중심의 짧은 bullet로 작성해줘.
- `발생 조건`은 trigger 조건만 작성하고, 원인 설명과 중복되는 문장은 `원인`에 둬줘.
- `수정 기준`은 구현 절차가 아니라 원인을 제거하는 판단 기준으로 짧게 작성해줘.
- `비고`는 원인 / 수정 / 수정 기준 반복을 피하고 유지할 주의점이나 후속 구조 참고만 남겨줘.
- 코드의 실제 타입명 / API / struct / enum / 파일명을 기준으로 작성해줘.
- 버그가 발생한 처리 흐름과 책임 경계를 추적 가능하게 설명해줘.
- 수정이 원인을 어떻게 제거했는지 연결해줘.
- 검증 결과는 실제 확인한 결과만 작성해줘.
- 관련 PR / 문서는 확인 가능한 항목만 작성하고, 없거나 확인되지 않은 항목은 만들지 말아줘.
- 관련 문서는 기본적으로 파일명만 작성하고, 같은 파일명이 여러 폴더에 중복될 때만 경로를 함께 작성해줘.
- 최상위 bullet 사이에는 빈 줄을 한 줄 넣고, 하위 bullet 사이에는 이 규칙을 적용하지 말아줘.

권장 구조:
1. 상단 메타
2. 요약
3. 영향 범위
4. 환경
5. 발생 조건
6. 재현 방법
7. 기대 결과 / 실제 결과
8. 원인
9. 수정
10. 수정 기준
11. 검증 결과
12. 회귀 방지 기준
13. 관련 PR / 문서
14. 비고
````

## 5. 작성 기준

아래 상단 메타와 섹션 구성은 `00_Document_Common_Format_Prompt`의 공통 양식을 Bug Report 기준으로 구체화한 양식이다.

```md
# UE5 Portfolio Bug Report

## 제목

**B##: 문제 제목**

## 날짜

**yyyy.mm.dd**

## 상태

- [x] **완료**

---

## 브랜치

- `branch-name`

---

## 요약

## 영향 범위

## 환경

## 발생 조건

## 재현 방법

## 기대 결과 vs 실제 결과

## 원인

## 수정

## 수정 기준

## 검증 결과

## 회귀 방지 기준

## 관련 PR / 문서

## 비고
```

```yaml
상단 메타
-> H1은 `UE5 Portfolio Bug Report`로 작성
-> 제목 섹션에는 파일명 넘버링과 같은 `B##:` 제목을 Bold로 작성
-> 날짜는 `**yyyy.mm.dd**`로 작성
-> 날짜가 확인되지 않으면 `**추가요망**`으로 작성
-> 상태는 `- [ ] **진행중**` 또는 `- [x] **완료**`로 작성
-> 상태와 브랜치 사이에는 `---` 구분선을 배치
-> 브랜치 섹션명은 `브랜치`로 작성
-> 브랜치는 단일 / 복수 모두 bullet list로 작성
-> 브랜치 값은 인라인 코드로 작성
-> 브랜치가 확인되지 않으면 `- **추가요망**`으로 작성
-> 최상위 bullet 사이에는 빈 줄을 한 줄 배치
-> 하위 bullet 사이에는 추가 빈 줄을 강제로 넣지 않음
```

```yaml
환경 섹션 항목명
-> 엔진:
-> 브랜치:
-> 관련 클래스:
-> 관련 컴포넌트:
-> 관련 에셋:
-> 관련 문서:
```

환경 섹션은 실제 문서에 필요한 항목만 사용한다. 항목명은 KR 기준으로 작성하고, `Branch`, `Related Class`, `Asset`, `Document` 같은 EN 항목명은 사용하지 않는다.

브랜치는 상단 메타의 브랜치 섹션을 기본 기준으로 삼는다. 버그 발생 환경을 설명하는 데 브랜치 정보가 별도로 필요할 때만 환경 섹션에도 작성한다.

```yaml
영향 범위
-> 버그가 영향을 준 기능 / 시스템 / editor 흐름을 짧은 대상 중심 bullet로 작성
-> 기존 증상과 수정 범위에서 확인 가능한 내용만 작성
-> `~에 영향을 준다` 반복 표현은 지양
```

```yaml
발생 조건
-> 재현 방법과 실제 결과에서 조건만 요약
-> 원인 분석과 중복되지 않도록 발생 trigger를 중심으로 작성
```

```yaml
수정 기준
-> 원인을 제거하는 판단 기준을 작성
-> 구현 세부 변경 목록을 반복하지 않고 판단 기준을 짧게 정리
```

```yaml
회귀 방지 기준
-> 검증 결과에서 재발 방지 확인 항목을 추출
-> 실제 검증 가능한 조건으로 작성
```

```yaml
관련 PR / 문서
-> Work List 또는 Issue Checklist:
-> PR:
-> Verification Log:
-> Portfolio Technical Document:
```

관련 PR / 문서는 Work List 또는 Issue Checklist를 PR보다 먼저 작성한다.
관련 문서 항목명은 연결한 파일의 카테고리에 맞춰 `Work List` 또는 `Issue Checklist`로 작성한다.
관련 PR / 문서는 확인 가능한 항목만 작성한다. 없거나 확인되지 않은 관련 문서는 항목을 만들지 않는다.
관련 문서는 기본적으로 경로를 제외한 파일명만 작성한다. 같은 파일명이 여러 폴더에 중복될 때만 경로를 함께 작성한다.

```yaml
비고
-> 원인 / 수정 / 수정 기준을 반복하지 않음
-> 문서에 남길 주의점, 설계상 의미, 후속 구조 참고만 작성
```

```yaml
검증 결과 내부 구분
-> 하위 구분은 `###`보다 `**런타임 검증 결과**` 같은 굵은 라벨 사용
-> 굵은 라벨 앞에는 별도 `---` 구분선을 넣지 않음
```

## 9. 제약 조건

```yaml
제약 조건
-> 신규 Bug Report 파일명에 `(KR)`을 붙이지 않음
-> `유형` 또는 `Type` 섹션을 만들지 않음
-> 상태를 `Resolved` 같은 EN 상태값으로 작성하지 않음
-> 브랜치 섹션명을 `Branch`로 작성하지 않음
-> 추정 원인은 추정으로 표시
-> 원인과 수정이 연결되지 않는 설명은 비고로 분리
-> 최신 구조를 과거 버그 원인으로 덮어쓰지 않음
-> 확인되지 않은 관련 문서 경로를 임의로 만들지 않음
-> 관련 문서 경로를 불필요하게 길게 작성하지 않음
-> 검증 결과 내부 구분을 불필요한 H3 섹션으로 만들지 않음
-> 굵은 라벨 앞에 별도 `---` 구분선을 넣지 않음
```

## 10. 모호성 처리 기준

```yaml
모호한 경우
-> 날짜가 확인되지 않으면 `**추가요망**`으로 작성
-> 브랜치가 확인되지 않으면 `- **추가요망**`으로 작성
-> 상태 판단이 어렵다면 `- [ ] **진행중**`으로 작성
-> 재현 근거와 추정 근거를 분리
-> 현재 코드 기준 참고 사항은 본문과 분리
-> 관련 PR / 문서가 없거나 확인되지 않으면 해당 항목을 작성하지 않음
```

## 11. 검증 기준

```yaml
검증 기준
-> 신규 파일명에 `(KR)`이 없는가
-> 파일명과 본문 제목의 `B##` 넘버링이 일치하는가
-> 상단 메타가 제목 / 날짜 / 상태 / 브랜치 형식으로 작성되었는가
-> 날짜가 `**yyyy.mm.dd**` 또는 `**추가요망**` 형태인가
-> 상태가 `- [ ] **진행중**` 또는 `- [x] **완료**` 형태인가
-> 상태와 브랜치 사이에 `---` 구분선이 있는가
-> 브랜치가 bullet list이고 브랜치 값이 인라인 코드인가
-> 환경 섹션 항목명이 KR 기준인가
-> `유형` 또는 `Type` 섹션이 없는가
-> 영향 범위가 증상과 수정 범위에서 벗어나지 않는 짧은 대상 중심 bullet인가
-> 재현 조건이 명확한가
-> 발생 조건이 trigger 중심이고 원인 설명과 중복되지 않는가
-> 원인과 수정이 연결되는가
-> 수정 기준이 구현 절차 반복이 아니라 원인 제거 판단 기준인가
-> 발생 조건과 회귀 방지 기준이 검증 결과와 연결되는가
-> 관련 PR / 문서가 확인된 항목만으로 구성되었는가
-> Work List 또는 Issue Checklist가 PR보다 먼저 작성되었는가
-> Work List / Issue Checklist 항목명이 연결 문서 카테고리와 일치하는가
-> 관련 문서가 기본적으로 파일명만 작성되었는가
-> 검증 결과 내부 구분이 굵은 라벨로 작성되었고 앞에 별도 구분선이 없는가
-> 비고가 원인 / 수정 / 수정 기준을 반복하지 않는가
-> 실제 수행한 검증과 미검증 항목이 분리되는가
```
