# Document Format Review Prompt

## 1. 목적

작성된 개별 문서 또는 소수 문서를 공통 문서 양식과 문서 타입별 작성 규칙 기준으로 단계적으로 검토한다.

이 Prompt는 문서 내용을 새로 작성하는 Prompt가 아니라, 이미 작성된 문서가 공통 양식과 각 문서 타입의 목적에 맞게 구성되었는지 점검하기 위한 개별 문서 품질 검토 Prompt다.

검토 범위는 문서 내부의 형식, 섹션 순서, 문체, 용어, 시점, 설명 흐름, Markdown formatting에 한정한다.

문서 간 역할 충돌, index 불일치, 문서군 참조 문제처럼 문서 운영 체계 차원의 문제는 직접 해결하지 않고 `Document_Set_Audit_Prompt` 검토 항목으로 분리한다.

---

## 2. 사용 시점

```yaml
사용 시점
-> 문서 작성 후 양식과 구조를 검토할 때
-> PR / Issue / Bug Report / System Architecture 문서의 제출 전 검토가 필요할 때
-> 공통 양식 기준과 문서 타입별 기준이 함께 적용되었는지 확인할 때
-> 문서군 전체 감사가 아니라 특정 문서 또는 소수 문서의 품질 검토가 필요할 때
```

---

## 3. 사용 방법

검토 대상 문서, 문서 타입, 기준 Prompt를 함께 제공한다.

검토는 공통 양식 → 문서 타입별 양식 → 문서 타입별 목적 → 문서 내부 일관성 → 검증 결과 순서로 진행한다.

---

## 4. 복사용 Prompt

````text
다음 Markdown 문서를 양식과 문서 타입별 작성 규칙 기준으로 단계적으로 검토해줘.

검토 대상:
- [문서 / 폴더 경로 입력]

문서 타입:
- [Issue Checklist / Bug Report / Pull Request / System Architecture / Technical Summary 등 입력]

기준 Prompt:
- 공통 양식: `00_Document_Common_Format_Prompt (KR).md`
- 문서 타입별 Prompt: [문서 타입별 Prompt 경로 입력]

검토 목적:
- [제출 전 검토 / 리팩터링 후 검토 / 개별 문서 양식 정렬 / 특정 규칙 확인 등 입력]

수정 허용 범위:
- [검토만 / 직접 수정까지 허용 / 특정 항목만 수정 등 입력]

## 1. 공통 양식 검토

먼저 검토 대상 문서에 적용되는 공통 양식 기준을 검토해줘.

검토 항목:
- 파일명과 본문 문서 ID가 충돌하지 않는가
- 상단 메타 섹션 순서가 일관적인가
- 제목 / 목적 / 관련 브랜치 / 날짜 / 상태 등 필요한 메타가 문서 타입에 맞게 배치되었는가
- 브랜치 표기가 실제 branch naming convention과 맞는가
- H2 / H3 인덱스 규칙이 일관적인가
- 주요 섹션 사이에 `---` 구분선이 적절히 사용되었는가
- 코드블럭과 평문 설명의 역할이 구분되는가
- 리스트 공백, 헤더 공백, 문서 끝 구분선이 일관적인가
- 문체가 문서 타입 기준과 충돌하지 않는가
- 코드 식별자 / 핵심 개념명 / 일반 EN 용어의 소대문자와 인라인 코드 표기가 공통 양식 기준과 맞는가

## 2. 문서 타입별 양식 검토

문서 타입별 Prompt 기준으로 섹션 구성과 순서를 검토해줘.

검토 항목:
- 해당 문서 타입에 필요한 필수 섹션이 있는가
- 섹션 순서가 기준 Prompt와 맞는가
- 문서 타입에 맞지 않는 섹션이 섞여 있지 않은가
- 관련 문서 / 브랜치 / 이슈 번호 / 검증 결과가 문서 타입에 맞는 위치에 있는가
- 후속 구조 안내, 구형 문서 안내, 안정성 보완, 버그 참조 등 특수 섹션이 필요한 경우 적절히 분리되었는가

## 3. 문서 타입별 목적 검토

문서가 해당 문서 타입의 목적을 수행하는지 검토해줘.

검토 기준:
- Issue Checklist: 작업 전 범위, TODO, 검증 기준이 명확한가
- Bug Report: 재현, 원인, 수정, 검증이 분리되어 있는가
- Pull Request: 변경 의도, 변경 범위, 테스트, 관련 문서가 읽히는가
- System Architecture: 기존 구조, 문제 / 한계, 구조 결정, 결과가 분리되어 있는가
- Technical Summary: 제출용 요약과 세부 문서 안내가 과하지 않게 정리되어 있는가

## 4. 문서 내부 일관성 검토

문서 내부의 용어, 시점, 구조 흐름을 검토해줘.

검토 항목:
- 같은 개념을 여러 이름으로 부르지 않는가
- 핵심 개념명과 일반 EN 용어의 소대문자 표기가 흔들리지 않는가
- 과거 브랜치 문서에서 최신 용어를 잘못 끌어오지 않았는가
- 구현된 구조, 당시 검토 후보, 후속 구조가 구분되어 있는가
- 기존 시스템 설명과 문제 분석이 섞이지 않았는가
- 리팩터링 방향과 실제 작업 내용이 구분되어 있는가
- 코드 타입명 / 함수명 / enum / struct 이름이 실제 코드와 맞는가
- 문서의 결론이 해당 문서에서 설명한 내용만으로 도출되는가

문서 간 역할 충돌, index 불일치, 문서군 참조 누락처럼 개별 문서 내부 품질을 넘어서는 문제는 `Document_Set_Audit_Prompt` 검토 항목으로 분리해줘.

## 5. 단계별 Findings 작성

Findings는 다음 순서로 작성해줘.

```yaml
1. 공통 양식 문제
2. 문서 타입별 양식 문제
3. 문서 목적과 내용의 불일치
4. 용어 / 시점 / 구현 근거 문제
5. 공백 / Markdown formatting 문제
6. 직접 수정 가능 항목
7. 후속 검토 항목
8. Document Set Audit으로 넘길 항목
```

각 finding은 다음 형식을 따른다.

```yaml
Finding
- 위치: [파일 / 섹션 / 문장]
- 문제: [무엇이 문제인지]
- 이유: [왜 혼동이나 품질 저하를 만드는지]
- 권장 수정: [어떻게 수정할지]
- 처리 구분: [즉시 수정 / 후속 검토 / 유지 권장 / Set Audit 이관]
```

## 6. 직접 수정 기준

수정까지 허용된 경우 다음 기준으로 직접 수정해줘.

직접 수정 가능:
- 헤더 번호 / 구분선 / 공백 / 코드블럭 언어 정리
- 문서 타입 기준에 맞는 섹션명 조정
- 명백한 오탈자, 중복 표현, 깨진 formatting 수정
- 공통 양식과 충돌하는 메타 섹션 정리
- 같은 의미의 용어 흔들림 정리

직접 수정 금지:
- 구현 여부를 근거 없이 확정
- 브랜치 시점이 다른 용어를 최신 용어로 강제 치환
- 문서 의도 자체를 변경
- 후속 구조를 당시 구현처럼 서술
- 코드 근거 없이 새로운 architecture 설명 추가

## 7. 검증

수정 또는 검토 후 다음을 확인해줘.

- 공통 양식 기준과 문서 타입별 기준이 충돌하지 않는다.
- 문서 타입별 필수 섹션이 유지된다.
- 문서 내부에서 시점과 용어가 흔들리지 않는다.
- 구현된 구조와 후속 제안이 분리되어 있다.
- Markdown 공백과 구분선이 일관적이다.
- 문서군 운영 체계 문제는 `Document_Set_Audit_Prompt` 검토 항목으로 분리되어 있다.
- `git diff --check`를 통과한다.

## 8. 결과 보고

다음 형식으로 결과를 요약해줘.

1. 검토한 문서
2. 적용한 기준 Prompt
3. 핵심 Findings
4. 직접 수정한 항목
5. 후속 검토 항목
6. Document Set Audit으로 넘길 항목
7. 검증 결과

제약 조건:
- 검토만 요청받은 경우 직접 수정하지 않는다.
- 문서 타입별 Prompt와 공통 양식 Prompt가 충돌하면 충돌 내용을 보고하고 임의로 판단하지 않는다.
- 브랜치 시점이 불명확하면 단정하지 말고 확인 필요로 남긴다.
- 코드 근거가 필요한 문서는 실제 코드 또는 해당 브랜치 기준 문서를 확인한다.
- 문서군 전체의 역할 / index / 참조 체계 문제를 개별 문서 수정으로 임의 해결하지 않는다.
````

## 5. 검토 단계

```yaml
1단계
-> 공통 양식 검토

2단계
-> 문서 타입별 양식 검토

3단계
-> 문서 타입별 목적 검토

4단계
-> 문서 내부 용어 / 시점 / 구현 근거 검토

5단계
-> 수정 가능 항목과 후속 검토 항목 분리

6단계
-> 문서군 운영 체계 문제를 Document Set Audit 항목으로 분리

7단계
-> Markdown formatting / git diff 검증
```

```yaml
-> 문서 타입별 내용 작성 기준
```
