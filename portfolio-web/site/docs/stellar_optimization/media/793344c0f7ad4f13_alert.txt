240: ## 80 Enemy 해석
241: 
242: 80 Enemy에서도 40 Enemy와 같은 경향이 유지됐다.
243: 
244: `AlertCap 40`에서 가장 크게 증가한 축은 `CharacterMovement p95`다.
245: 
246: ```text
247: 0.8072ms -> 1.6427ms
248: +0.8355ms
249: ```
250: 
251: Frame / Game p95도 함께 증가했다.
252: 
253: ```text
254: Frame p95: 17.5270ms -> 19.1846ms
255: Game p95 : 17.5329ms -> 19.1422ms
256: ```
257: 
258: BT Tick p95와 AIContext p95는 증가하지 않았다. 호출 수는 AIContext Count만 소폭 증가했고, AIIntent Count는 오히려 소폭 감소했다. 따라서 80 Enemy에서도 주된 차이는 BT service 호출 수가 아니라 Alert 대상 증가에 따른 movement / animation work다.
259: 
260: Actor / Tick count는 고정되어 있으므로, 이번 비교는 객체 수 차이가 아니라 assignment cap이 실제 행동 후보 수를 조절한 결과로 본다.
261: 
262: ## 최종 결론
263: 
264: 40 / 80 Enemy 모두에서 `AlertCap 40`은 `AlertCap 6`보다 `CharacterMovement p95`를 크게 증가시켰다.
265: 
266: ```text
267: 40 Enemy: 0.5394ms -> 1.3609ms (+0.8215ms)
268: 80 Enemy: 0.8072ms -> 1.6427ms (+0.8355ms)
269: ```
270: 
271: Frame / Game p95도 두 조건 모두 `AlertCap 40`에서 증가했다.
272: 
273: 따라서 Alert assignment cap은 Runtime LOD v1에서 유지할 가치가 있는 핵심 정책으로 본다. 효과의 본질은 BT Tick 자체를 크게 줄이는 것이 아니라, Alert movement 후보와 그에 딸린 CharacterMovement / animation work를 제한하는 것이다.
274: 
275: 후속 작업에서는 이 cap을 고정한 상태에서 Observe / Aware 상태 분리 또는 Collision / Feedback 축 측정으로 넘어간다.
